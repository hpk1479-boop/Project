# 시스템 컨트롤 상태·로그·전략 설정 속도 수정

## 변경

- `전체 종료` 버튼의 확인 창을 제거했다. 버튼을 누르면 기존 종료 작업을 바로 시작한다. 창 닫기의 자동 전체 종료 동작은 유지했다.
- 김비서 상태는 텔레그램 `getUpdates` 접속 결과로 표시한다. 첫 정상 응답 전은 `연결 대기`, 정상 응답 후는 `작동 중`, 접속 실패는 `오류`다. STAFF·이벤트 엔진·COMPOSER의 상태로 김비서 연결을 추정하지 않는다. 텔레그램 업데이트 처리 오류는 접속 실패와 구분한다.
- LIVE 시작 시 실제로 선택된 SPECIAL1~7 목록을 진단 서비스에 전달한다. 선택된 전략은 `작동 중`, 제외된 전략은 `연결 대기`, 선택된 전략에서 기록된 처리 오류는 `오류`로 표시한다. 설정 변경은 기존처럼 다음 엔진 시작 시 적용된다.
- 전략 설정의 SPECIAL별 상태 문구를 클릭 가능한 버튼으로 바꾸고 별도의 `추적 로그` 버튼을 제거했다. 어느 SPECIAL 버튼을 눌러도 공통 로그 창 하나를 재사용하며, 맨 위 `모두 보기`와 `SPECIAL1~7` 목록을 제공한다. 클릭한 SPECIAL을 자동 선택한다.
- 전략 설정 열기 전에 `Part1` 전체를 재귀 검색하던 경로를, 알려진 `program/event_host.py`의 직접 확인으로 바꿨다. 해당 파일이 없는 비표준 배치에서만 기존 검색을 사용한다.

## 검증

- 네트워크를 쓰지 않는 가짜 HTTP 응답으로 김비서 `연결 대기 → 작동 중 → 오류`와, 업데이트 처리 오류가 연결 상태를 끊지 않는 경우를 확인했다. 실제 텔레그램 메시지는 보내지 않았다.
- Tk 화면 확인: SPECIAL 상태 버튼 7개, 별도 `추적 로그` 버튼 0개, `모두 보기`와 SPECIAL1~7을 가진 공통 창 1개, SPECIAL1에서 SPECIAL2 클릭 시 같은 창 재사용을 확인했다.
- 로컬 진단 Named Pipe로 SPECIAL 선택 목록과 텔레그램 상태가 UI 읽기 경로까지 전달되는지 확인했다.
- 가짜 종료 스레드로 `전체 종료`를 눌렀을 때 확인창 없이 기존 종료 작업이 시작됨을 확인했다. 실제 프로그램을 강제 종료하지 않았다.
- 동일한 Python 실행 환경에서 경로 탐색 1회 측정: 기존 재귀 검색 222.64ms, 직접 확인 0.12ms. Tk 전략 설정 창 구성은 별도 1회 측정에서 39.7ms였다. 참고 측정이며 성능 게이트는 아니다.
- 변경한 Python 파일 및 신규 테스트 파일 8개의 문법 검사 통과. 관련 회귀 테스트를 추가했다. 로컬 Python에 `pytest`가 없어 pytest 묶음은 실행하지 못했으며, 위의 독립 실행 검증으로 변경 경로를 확인했다.
- Part1 소스 6개를 `58-control-special-telegram-ui` 무결성 체인에 등록하고 `build/part1_immutable_sha256.json`의 해당 항목을 갱신했다. 새 해시 체인 오류 0건. 기존 미등록 진단 6건은 변경하지 않았다.
