## 2. 보존 조건과 캐시 수명

⑥-A 캐시는 매번 관측을 받을 때 새로 만듭니다. 시각이 같은 ROW 갱신에서도 이전 관측의 딕셔너리를 재사용하지 않습니다. 원본 공유 피드 레지스트리를 변경하지 않으며 `current.views.update()`는 각 계산기의 별도 딕셔너리에 입력을 반영합니다. 활성 거래 순회와 중단 검사 위치는 그대로입니다.

⑥-B는 진입 전에는 목표가격을 만들지 않습니다. 역크로스로 취소되거나 위험폭이 0인 거래, 대기 중인 거래에는 이 캐시가 없습니다. 계산식은 `entry + (1 if LONG else -1) * rr * risk`의 원래 연산 순서를 유지합니다. 1분봉 확정 조건, 종료 시각의 배타적 경계, 손절·익절 동시 접촉 시 손절 우선은 바꾸지 않았습니다.

캐시된 목표가격 9개는 **모든 RR 청산이 완료되면 삭제**합니다. 일부 RR만 종료된 거래는 나머지 판정을 위해 보관합니다. 이 Python 환경에서 별도 목표가격 딕셔너리와 float 객체 크기의 합은 미청산 진입 거래당 약 **568바이트**였습니다. 부모 딕셔너리·메모리 할당기 비용은 제외한 값이며 전체 프로세스 메모리 증가량은 아닙니다. 청산된 거래에 캐시가 계속 쌓이지 않습니다. 상세 CSV의 `target`은 기존처럼 해당 RR가 실제 종료됐을 때만 출력합니다.

⑥-C는 `results()` 호출마다 집계하므로 중단·부분 결과 이후 상태가 바뀌면 새 값을 반영합니다. 다른 RR의 결과나 이전 `results()` 결과를 영구 캐싱하지 않습니다.

## 4. 막힌 항목과 처리

**⑦ 해시 읽기 버퍼:** 4 MiB `readinto` 후보를 측정하고, 256 KiB 후보로 한 번 더 시도했습니다. 기존 SHA-256과 결과는 같았지만 두 후보 모두 작은 파일에서 느려졌고 큰 파일에서도 일관된 이점이 없었습니다. 예를 들어 두 번째 후보는 4 KiB 파일에서 약 42.60% 더 오래 걸렸고, 64 MiB 파일의 감소는 약 0.40%, 256 MiB 파일은 약 1.70% 증가했습니다. 파일시스템 캐시가 데워진 Linux 합성 실험입니다. **운영 `settings.py`는 변경하지 않았습니다.** 전체 파일 검증을 줄이거나 크기/mtime 기반 해시 캐시를 복원하지 않았습니다.

**DuckDB 검사:** 설치를 두 번 시도했지만 현재 환경에서 패키지를 가져오지 못했습니다. `test_build_stop_saves_completed_pieces` 실패 1개와 `test_part2_event_runner.py` 수집 오류 1건을 각각 한 번 재시도하고, 수정본43에서도 같은 오류를 확인했습니다. 전략·스키마·운영 DB 코드를 바꿔 통과시키지 않았습니다. 검증용 기존 37·39·43 도구 일부의 SQL import 우회는 실제 SQL 검증으로 집계하지 않습니다.

**기존 무결성 불일치:** Part1 검사에 있던 7건이 수정본43·44에서 동일합니다. 해당 파일들을 수정하거나 무결성 목록을 임의 승인하지 않았습니다. 이번 운영 수정은 Part2 한 파일뿐이므로 Part1 해시 변경 이력을 추가하지 않았습니다.

검증 중 외부 실행 명령 제한으로 검사 묶음 실행이 마지막 모듈의 첫 오류 기록 뒤 중단된 적이 있습니다. 이미 완성된 첫 XML/로그를 보존하고 그 모듈만 한 번 재시도해 결과표를 완성했습니다. 테스트 실패를 숨기거나 중단된 실행을 통과 처리하지 않았습니다.
