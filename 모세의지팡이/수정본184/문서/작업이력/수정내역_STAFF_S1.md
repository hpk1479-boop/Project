# 수정본8 — S1 순수 Fact 이전

수정본7 전체 4,188개 파일을 복사하고 `검증결과/staff_s1/s0_frozen_manifest.json`에 SHA256을 고정했다. 수정본7 원본 및 수정본8 안에 복사된 S0 증거는 갱신하지 않는다. S0 골든과 expected 파일은 변경하지 않는다. 동작 검증 assertion을 유지하며 성능 1개는 사용자 후속 지시의 고정 반복 측정 규칙을 적용한다.

## 구현 범위

- STAFF의 9개 순수 함수를 본문 그대로 이전했다. EMA slope·ATR14·basis slope·legacy SuperTrend는 `indicator_facts`, 4종 percentile/regime 상태는 `monitor_OZ`, legacy FVG는 `strategy_FVG` 소유다. STAFF는 기존 함수 이름으로 import하며 적용 순서와 응답 스키마를 유지한다.
- `indicator_facts.FACTS`에 `ATR14_GENERAL`을 기존 TR → rma(14) 의존성으로 등록했다. STAFF 응답의 기존 `add_atr14_feature`는 AST 그대로 이전해 실행한다.
- FVG의 `_wilder_atr` 본문은 그대로 두고 이름만 `FVG_WILDER_ATR`로 명시했다. 기존 `_wilder_atr`은 동일 함수의 별칭이다. 공용 ATR과 합치지 않았다.
- Part2/Part3 `calculations/common.py`의 중복 Fact 함수는 새 소유 모듈의 함수 객체를 다시 내보낸다. 기존 `derived.py`는 common을 다시 내보내므로 수정하지 않는다. Part3에는 기존 Part2와 동일한 LIVE import 어댑터를 추가했다.
- Watch MA 계산은 이미 `watch_ma`/`indicator_facts`, 이력 관리 어댑터는 `watch_ma_features`에 있다. 그 파일과 이력·epoch 규칙은 그대로다. 클라이언트로 캐시 사용처를 바꾸는 작업은 S4b 범위다.
- 원비 함수·상수·설정·호출, 매니저, SPECIAL, EA는 바꾸지 않는다. S2 저장 구조·wire 변경도 하지 않는다.
- audit 어댑터의 import 순서만 새 의존성에 맞췄다. audit 테스트 입력·기대값·assertion은 그대로다.

## 불변 증거 및 무결성

골든 비교는 SQLite read-only로 열며 기록기는 `staff_s0` 경로에 새 결과를 쓰는 것도 거부한다. S1 산출물은 별도 `staff_s1`에만 저장한다. 기록하는 것은 S1 실제 응답이며 S0 기대값을 재생성하지 않는다.

기존 audit 해시 체인은 S0와 이미 29개 항목이 불일치했다. 사용자의 후속 지시로 `21-s0-fact-source-anchor`에 이번에 이전한 4개 소유 파일의 실제 S0 해시만 명시적으로 연결하고, `22-s1-pure-facts`에 S0→S1 변경을 등록했다. 원래 manifest와 과거 단위는 수정하지 않았다. 이 4개 진단만 해소되고 다른 기존 오류 25개는 남으며 새 오류나 끊어진 체인은 없다. 모든 기존 변경을 일괄 승인하지 않았다. 추가 전체 변경 기록은 `source_delta.json` 및 `Part1/audit/remediation/30-staff-s1/s0_to_s1.json`에 둔다. `build/part1_immutable_sha256.json`은 S1 소스 목록으로 재생성한다. **S0 골든·expected 결과 파일 갱신과는 별개**다.

개발 중에는 영향 함수 AST, ATR 분리, 원비·MA 보존, import 및 기존 STAFF 응답 테스트만 실행한다. 구현 완료 후 G1/G2/G3/성능 게이트를 각 1회 실행하고, 실패 원인을 확인해야 할 때만 해당 검증을 재실행한다. S2는 시작하지 않는다.

## 최종 비교에서 발견한 S0 기록 형식 문제

OZ `_observed_encode`는 `set`/`frozenset`을 타입 태그와 순서가 있는 배열로 기록했다. Python 프로세스마다 해시 순서가 달라 S0와 이번 실행 사이 14개 집합의 DI/STO 순서(28개 원소 위치)가 바뀌었다. 수정 전 S0 코드 재실행과 S1 LIVE/BACKTEST 모두 같은 차이를 보였고, 알림·이벤트·집합 구성원은 동일했다.

S0 및 S1 원시 기록과 해시는 변경하지 않았다. `staff_golden/parity_compare.py`에서 **OZ 상태의 명시적 set/frozenset 태그만** 타입에 맞게 비교한다. 일반 목록·tuple·dict 항목 순서, 집합 구성원·중복·타입, 알림 차이는 계속 실패한다. 세 음성 대조 테스트를 추가해 해당 비교 수정만 실행했고 통과했다. 3-way 시나리오 실행을 반복하지 않고 이미 생성된 파일을 재비교해 세 경로 모두 S0 상태와 동일함을 확인했다. 원시 해시의 차이와 비교 정책은 `parity_diagnosis.json`, `parity_s0_compare.json`에 남긴다.

`Part2/validation_suite/test_oz_fvg_optimization.py`의 과거 fixture는 옛 OZ/FVG만 현재 프로그램에 덮어써 S1 import에 필요한 Fact 함수가 없어졌다. 최초 전체 G1의 14개 오류는 이 입력 조립 문제였다. 옛 STAFF만 추가하는 중간 시도는 사용자 지적에 따라 중단했으며 결과로 채택하지 않는다.

## 성능 측정 규칙 고정 — 사용자 후속 지시

단발 wall 측정은 S0 117.3468초, S1 118.8382초로 기존 성능 검사에서 실패했다. 동작 13개는 통과했다. 초기 STAFF +5% 개별 지표 실패와 이 13/14 결과는 삭제하거나 성공으로 덮어쓰지 않는다.

사용자 지시에 따라 성능 검사 1개를 삭제하지 않고 반복 CPU 비교로 바꾼다. 전후 6개·LIVE/백테스트 6개·시나리오 1개 assertion은 그대로 유지한다. 성능 함수의 Fact 재사용 assertion도 유지하며 5개 후보 표본 각각에 적용한다. `run`에는 동일 계산 구간의 process_time 시작/끝과 cpu 반환만 추가하고, summary 직렬화에서 cpu를 숫자로 유지한다.

후보를 측정하기 전에 고정한 산식: 동결 S0를 독립 프로세스로 5회 측정한다. 6개 작업별 CPU 중앙값에 대한 최대 절대 편차의 최댓값을 d라고 할 때, 허용 비율은 `ceil(100 * (1 + max(0.05, 2*d))) / 100`이다. 2배 여유와 1% 단위 올림을 쓰되 1.10을 넘으면 측정 환경 불안정으로 실패시키며, 자동으로 한도를 넓히거나 좋은 표본만 고르지 않는다. 이 산식은 S1 후보의 값을 보기 전에 등록했다.

그 뒤 S0 → 후보 순서로 5쌍을 교대 실행한다. 각 작업의 후보 CPU 중앙값 / 같은 세션 S0 CPU 중앙값이 잠긴 비율 이하여야 한다. 비교 중 S0 중앙값 자체가 보정 측정 중앙값의 허용 범위를 벗어나도 실패한다. parser 1,000회, 각 요청 250회, 기존 OZ/FVG LIVE 시나리오 240초 전체를 측정한다. 각 프로세스는 동일 warmup을 적용하며 GC는 켜 둔다. 짧은 작업의 Windows CPU 시간 양자화 영향을 줄이기 위해 STAFF 배치를 기존의 5배로 늘렸다. wall/p50/p95는 원시 진단 자료로 보존한다.

`build/staff_performance_protocol.py`, `performance_protocol/preregistered.json`, `locked_rule.json`이 규칙과 해시를 기록한다. 숫자 한도까지 동결한 뒤 S8까지 같은 방법·한도를 사용하며 단계별로 다시 보정하지 않는다. S0 골든이나 expected 결과를 다시 만들지 않는다.

### S0 보정 실패 원인 분석과 CPU 고정

CPU 이동을 허용한 첫 S0 보정 5회는 최대 중앙값 대비 편차 약 47%로, 사전 산식상 1.95라는 무의미하게 큰 한도가 필요했다. 미리 둔 1.10 상한에 따라 보정은 FAIL이며 이 규칙을 채택하지 않았다. `performance_protocol_unpinned`에 5개 표본·원래 runner·실패 lock·로그를 모두 보존한다. 후보는 한 번도 측정하지 않았다.

해당 PC는 i5-14500이며 측정 프로세스 affinity는 20개 논리 CPU 전체(1048575)였다. 서로 다른 CPU 배치의 영향을 확인하기 위해 v2에서는 **벤치마크 worker 자신만** 허용된 가장 낮은 논리 CPU에 고정한다. 다른 앱, MT5, 전원 설정, 프로세스 우선순위는 바꾸지 않는다. CPU 배치가 실제 원인이라는 단정은 하지 않으며 고정 후 S0 반복 값으로 확인한다.

숫자 한도 동결 이전의 보정 실패를 해결하는 변경이다. 표본 수·작업량·CPU 중앙값 비교·한도 산식·10% 상한은 그대로 유지한다. 후보의 성능을 본 뒤 기준을 바꾸지 않는다. 안정된 보정으로 확정된 v2 방법과 숫자만 S1–S8에 동일하게 적용한다. 성능 판정 코드의 양성·음성 대조 6개(변동 폭 산정, 상한 실패, 회귀 실패, 환경 이동 실패, 5쌍 유지)가 통과했다.

## 최종 사용자 지시: 성능은 S5·S8 종료에서만 판정

CPU 고정 S0 5회를 완료했다. 추가 후보 5쌍 측정은 실행하지 않았다. 최초 공통 10% 상한 보정은 request_0의 7.407% 최대 편차 때문에 FAIL이며 그 파일은 그대로다. 최종 정책은 완료된 표본에 사전의 두 배 편차 산식을 **작업별** 적용해 1.05/1.15/1.09/1.06/1.09/1.06으로 확정했다. 전체 시나리오는 73.8125–76.046875초, 중앙값 74.171875초, 최대 편차 2.528%여서 허용 비율 1.06이다. 정확한 표와 운영 방법은 `성능규칙_S1_S8.md`에 있다.

이 최종 지시는 위의 모든 단계 성능 게이트 계획을 대체한다. S1–S4·S6–S7은 성능 1회 참고 기록만 남기고, 결과 동일성 및 새 실패 0으로 완료 여부를 정한다. 성능 항목을 삭제하지 않았으며 Fact 재사용 검사를 유지한다. 수정본6 전체 BEFORE, 동작 13개 AST, 총 14개 검증 항목도 유지한다. 변경한 성능 항목만 저장된 1회 결과로 확인했고 새 정책 음성 대조 4개도 통과했다.

`build/compare_staff_golden.py`를 추가했다. 파일 SHA256이 같으면 동결 골든과 바이트가 같음을 사용하고, 다를 때 기존 정확 비교로 진행한다. 동일·차이·누락 입력 3개 관련 검증이 통과했다. 이미 완료한 S1 골든 실행이나 S0 생성은 다시 하지 않았다.

최종 S1: 합성 33,996개 사례 / DataFrame 19,160개, 실제 MT5 4,542개 사례 / DataFrame 4,302개 동일. 3-way와 전체 baseline signature 동일, 새 동작 실패 0. Part2 전체 745개 수집이며 기존 715개 ID 누락 0. 기존 실패/오류는 baseline 기록대로 남는다. S0·expected·원비는 변경하지 않았다.
