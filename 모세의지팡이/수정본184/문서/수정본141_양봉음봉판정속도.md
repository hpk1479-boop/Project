# 수정본141 양봉·음봉 판정 속도

기준: 2026-10-07 사용자 요청("단일 프레임 백테스팅 속도가 안 빨라졌지?" → 측정 → "응 작업시작해"). 수정본140을 복사해 시작했고, 140의 검증결과는 가져오지 않았다.

## 원인 (140 측정, `검증결과/revision140/measurement`)
- SPECIAL9 이틀치(준비 3거래일 포함 1분봉 6,889개)를 py-spy로 재 보니 CPU의 약 64%가 레시피 엔진의 양봉·음봉 판정(`CANDLE_STATE`)에 들었다.
- 판정할 봉 하나만 보면 되는데, 새 1분봉이 확정될 때마다 1분봉 이력 전체(수천 개)의 캔들 값을 처음부터 봉마다 다시 계산하고 있었다. 엔진이 쓰던 계산 틀(`ArrayFactFrame`)은 봉이 바뀌면 값을 비우고 0번 봉부터 다시 계산한다.
- 이 방식은 양봉·음봉 조건을 만든 수정본107부터 있었고, 140에서 SPECIAL9에 "터치한 봉이 음봉" 조건이 들어가며 SPECIAL9에 걸렸다. 140의 망치형 판정도 같은 방식이었다.
- 처음에 짐작한 "안 쓰는 시간봉 처리"는 3~5%로 주원인이 아니었다.

## 바뀐 것
- `Part1/program/strategy_recipe/port.py`의 `_candle_fact`: 판정하는 봉의 시가·고가·저가·종가로 공용 계산 함수(`candle_direction_values`, `candle_shape_values`)를 한 번 부른다. 두 값 모두 봉 하나만 쓰는 공식이라 전체 이력을 계산한 값과 같다. 가상진입이 확인봉을 판정하는 방식과도 같다.
- 쓰지 않게 된 캐시(`candle_frames`)를 지웠다.
- 라이브도 같은 코드를 쓰므로 라이브 CPU도 같이 줄어든다.
- 판정 결과는 바뀌지 않는다(아래 시험과 실제 녹화 비교).

## 결과 (`검증결과/revision141/measurement`)

같은 이틀치(XAUUSD+ 2026-09-15~09-17, 준비 3거래일), 프로세스 1개, py-spy 없이. 실제 백테스트 작업자처럼 Windows 절전을 풀고(`process_priority.full_speed`) 140·141을 번갈아 두 번씩 쟀다.

| | 140 | 141 |
|---|---|---|
| 걸린 시간 | 49.4초, 50.1초 | 21.5초, 21.2초 |
| 1분봉 하나 CPU | 7.0ms | 3.0ms |
| 그중 엔진(전략 판단) | 4.6ms | 0.46ms |

- 이틀치 기준 약 2.3배, 엔진 처리는 약 10배 빨라졌다. 사용자가 돌린 6년치(약 45분)는 엔진 비중이 비슷해 약 20분 안팎이 될 것으로 본다(다시 돌려 확인 필요).
- 처음 측정(140 121초, 141 35~40초)은 측정 프로세스가 Windows 절전에 걸린 상태라 비교에 쓰지 않았다. 같은 코드도 CPU 시간이 두 배 넘게 달랐다.
- 이제 남은 시간은 대부분 녹화 읽기다: 녹화 풀기 약 42%, 자료 해석 약 21%, STAFF 정리 약 7% 등 83%. 엔진은 9%.
