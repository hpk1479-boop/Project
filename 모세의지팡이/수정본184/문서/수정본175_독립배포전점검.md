# 수정본175 독립 배포 전 점검

2026-10-09 수정본175를 읽기 전용으로 점검한 결과다. 높은 심각도 3건과 보통 3건을 확인했으며, 점검 당시에는 배포 보류를 권고했다. 사용자가 후속 수정을 요청하여 이 보고서는 수정본176에 보관한다. 아래 파일 경로와 줄 번호는 **수정 전 수정본175 루트 기준**이다. 수정 결과는 별도 수정본176 문서에 기록한다.

## 점검 범위와 제약

루트 CLAUDE.md와 수정본171~175 변경 문서를 먼저 읽었다. 라이브와 재생의 시간 경계, 최근 사건 기간, 재생 재사용, 가상진입 종료, 통합설치의 코드 묶음과 보존 규칙, 경로 이식성을 검토했다.

수정본175, 실제 설치본과 데이터창고를 수정하지 않았다. 실행은 임시 복사본과 합성 자료에서만 했고, 각 전체 시험은 285초 제한을 뒀다. 시험 시작 전 MOSES.exe가 실행 중이지 않음을 확인했다. 실제 EXE 빌드, 설치, 배포와 업데이트는 하지 않았다. 점검 대상 코드·설정·문서 1,486개는 점검 전후 해시가 같았다.

## 확인한 문제

### 1 설치본 전략 변경 후 이전 알림 재사용

- 심각도: **높음**
- 위치: `Part2/event_backtest/runner.py:66` 및 재사용 조회 `:569`
- 문제: `code_hash()`가 설치본의 `스페셜/기본`과 `스페셜/내 전략`을 빠뜨린다. 같은 번호 전략의 조건을 바꿔도 재사용 키가 같아 이전 알림을 가져올 수 있다. 새 실행의 당시 설정에는 바뀐 조건이 기록되므로 결과 해석도 잘못된다.
- 재현: 임시 설치형 폴더의 `SPECIAL100.recipe.json`에서 기간을 50에서 60으로 변경했다. 레시피 해시는 달랐지만 코드 해시와 재사용 키는 같았다. 첫 실행은 재생 조각 3개, 두 번째는 0개였으며 이전 결과를 복사했다. 두 번째 당시 설정에는 60이 기록됐다. 기본 전략 폴더에서도 같은 원인을 확인했다.
- 직접 재현: **확인**. 재생 작업만 모의 처리했고 레시피 로딩, 해시, 재사용 판정과 DuckDB 복사는 실제 코드를 사용했다. 실제 시장 재생 결과를 대조한 것은 아니다.

### 2 최근 외부유동성 터치 기간 시작 오류

- 심각도: **높음**
- 위치: `Part1/program/strategy_recipe/port.py:594`, 기간 기억 `:738`
- 문제: SWEEP의 `touch_time`은 확정봉의 시가 시각인데 포트가 이를 사건 기간의 시작으로 사용한다. 수정본173의 “사건이 판정된 순간부터 시작” 규칙과 다르다.
- 재현: 10:00~11:00의 1시간봉 터치를 11:00에 처음 확인해도 `recent: {"seconds": 1800}`은 10:00부터 계산돼 즉시 거짓이 됐다. 최근 터치 조건과 취소가 필요한 순간에 작동하지 않는다.
- 직접 재현: **확인**. 실제 `LiquidityDetector.process`의 사건을 `IntentPort.handle_fact`로 전달했다. 기억한 시각은 판정 시각보다 3,600초 전이었다. 같은 시작 시각을 쓰는 순차 연쇄도 영향 가능성이 있지만, 점검에서는 연쇄까지 별도 실행하지 않았다.

### 3 이전 세션 고저가 전환 지연

- 심각도: **높음**
- 위치: `Part1/program/event_engine/sweep_levels.py:43`
- 문제: 세션 선택에 마지막 확정 5분봉의 시가 시각을 사용한다. 런던 시작이 16:00이면 이전 세션 고저가는 16:05부터 생긴다. 뉴욕 21:00에도 21:05까지 런던 기준을 사용한다. 이미 지나간 1분봉 터치는 나중에 재판정하지 않는다.
- 재현: 이전 세션 고가를 110으로, 16:00의 1분봉 고가만 111로 입력했다. 의도한 고가를 제공하면 16:01에 터치 1건이지만 실제 레벨 경로에서는 0건이었다. 16:05에 레벨이 생긴 뒤에도 0건이었다.
- 직접 재현: **확인**. 공용 레벨 함수와 실제 SWEEP 판독기로 재현했다. 기존 서버 시간 시험은 20시·22시 사례여서 이 정각 경계를 잡지 못했다.

### 4 가상진입 마지막 확정봉 누락

- 심각도: **보통**
- 위치: `Part2/event_backtest/virtual_entry.py:237`
- 문제: 종료 정각의 관측을 `observe()` 전에 버린다. 해당 관측으로 확정되는 기간 내 마지막 1분봉의 손절·익절도 빠져 미청산으로 남는다. 보유 데이터 구간별 끝 경계에도 해당한다.
- 재현: 합성 MSD2 녹화에 23:59와 다음 날 00:00 관측을 기록했다. 매수가 10, 손절 8, 마지막 봉 고가 25·저가 9였다. 종료일을 다음 날로 계산하면 RR 9개 모두 `UNCLOSED`; 같은 녹화를 동일한 종료 경계로 판독기에 전달하면 모두 `WIN`이었다.
- 직접 재현: **확인**. 실제 녹화 읽기와 `calculate()` 경로를 사용했다. 실제 창고 자료는 쓰지 않았다.

### 5 Windows 가상환경 Python의 관리 프로세스 식별 실패

- 심각도: **보통**
- 위치: `Part3/lab/backtest_supervisor.py:303`, 부모 기록 `Part3/lab/backtest_jobs.py:348`
- 문제: 부모가 기록한 실행기 PID와 실제 스크립트 PID가 같아야 한다고 검사한다. Windows 가상환경 실행기는 별도 Python 프로세스를 시작하므로 실행 기록과 실제 프로세스가 다르다는 오류로 백테스트가 시작되지 않는다.
- 재현: 기본 Python은 Popen PID와 스크립트 PID가 같았지만 Windows 가상환경 Python은 달랐다. 공식 검사 3파일·4건이 이 조건에서 실패했다. 같은 의존성을 사용한 기본 Python에서는 해당 파일 46개가 모두 통과했다.
- 직접 재현: **확인**. 가상환경 Python을 실행기로 선택한 환경의 문제다. 기본 설치본은 별도 실행기를 사용하므로 실제 설치 EXE에도 같은 문제가 있다고 확인한 것은 아니다.

### 6 배포 AI 규칙의 기간 안내 오류

- 심각도: **보통**
- 위치: `통합설치/releasekit/agent_rules.md:29`
- 문제: 규칙은 입력 기간을 UTC 날짜라고 안내하지만 실제로는 녹화의 브로커 서버 날짜다. AI가 UTC 기간 요청을 그대로 명령에 넣으면 다른 구간을 시험한다.
- 재현: 기본 브로커 설정에서 `2026-09-01~2026-10-01`은 실제 UTC로 `2026-08-31 21:00~2026-09-30 21:00`이다. 문서의 “UTC 9월 전체”와 3시간 다르다.
- 직접 재현: **확인**. 임시 사본의 실제 시각 변환 함수로 확인했다. 수정본172 문서가 기존 화면의 UTC 문구를 남겼다고 기록한 점과 별개로, 새 배포 AI 지침도 같은 잘못된 설명을 담고 있다.
