# 시스템 컨트롤 상태·종료와 STAFF 재연결

## 변경

- 모듈 버튼과 상태 창은 `연결 대기 / 작동 중 / 오류`만 표시한다. 처음 연결 전과 정상 종료 후는 연결 대기, 실행 중 파이프 끊김·지연·처리 실패는 오류다. OZ·SWEEP·FVG·INDICATOR·WATCH는 실제 감시 상태가 있을 때만 작동 중으로 표시한다. 로그 시각만으로 작동 중을 판단하지 않는다.
- 시스템 컨트롤 창의 닫기 동작은 전체 종료 작업을 실행하고 끝난 뒤 창을 닫는다. 시작 작업이 진행 중이어도 그 작업 완료 후 종료하도록 직렬화했다. 종료 실패 시 창을 유지하고 오류를 보여 준다.
- EA는 STAFF 재연결 때 모든 피드에 개별 FULL 필요 표시를 한다. 각 피드의 첫 전송이 승인된 뒤에만 표시를 지워, 첫 묶음에 없던 시간봉이 ROW/HEARTBEAT부터 보내지는 문제를 막는다. Wire 형식과 전략 판정은 바꾸지 않았다.
- `STAFF_Wire_Schema.mqh`의 EA 빌드 해시를 변경된 소스 기준으로 갱신했다. schema_id와 열 목록은 그대로다.

## 검증

- 상태·닫기·STAFF 재연결 관련 테스트: 11개 통과. 빌드 해시 확인 시험 1개 추가 통과. 네트워크 전송은 차단했다.
- MetaEditor EA 최종 컴파일: 오류 0, 경고 0. 수정본30의 EX5를 생성하고, 설치된 MT5 프로필 중 해당 EA가 있던 유일한 프로필에 MQ5·MQH·EX5를 백업 후 복사했다. 복사본 해시는 빌드와 일치한다. 이전 빌드는 `검증결과/control_status_reconnect/mql_compile/`과 `검증결과/control_status_reconnect/installed_backup/`에 보존했다.
- 실제 터미널은 실행 중이 아니어서 LIVE 재시작 시험은 하지 않았다. 테스트 중 텔레그램 전송도 하지 않았다.
- 추가로 실행한 엔진 관련 테스트 35개 중 34개 통과, `test_bar_close_fact_ignores_forming_updates_until_new_bar` 1개 실패. 이 시험은 diagnostics를 연결하지 않으며 이번 엔진 변경은 diagnostics가 있을 때만 실행된다. 실패는 Fact 봉마감 무효화 계층에서 `computed=2`가 되어 기대값 1과 다른 기존 독립 문제로 분류한다. 판정식은 수정하지 않았다.
- `57-control-status-reconnect` 해시 체인 등록과 현재 Part1 추적 파일 해시 불일치 0건. 이전 UI 변경의 미등록 연결부는 `56a-ui-state-prior`에 별도 기록했다. 기존 무결성 진단 6건은 그대로 남았다.

## 현행 김비서 상태 표시의 의미

- `김비서 · 작동 중`은 STAFF 파이프가 연결되어 있고 이벤트 엔진이 시장 묶음을 한 번 이상 처리했으며 김비서 오류가 기록되지 않았을 때 표시하는 간접 상태다. COMPOSER 연결, 김비서 출력 작업의 생존, 텔레그램 전송 가능 여부를 직접 확인한 표시는 아니다.

## 김비서 상태 후속 요청 (미구현)

- 김비서 버튼의 `작동 중`은 텔레그램 연결 확인 결과로 표시한다. 기존 `getUpdates` 응답의 성공 여부를 상태에 반영하고, 첫 성공 전에는 `연결 대기`, 연결 실패 시에는 `오류`로 표시한다. 시장 데이터 처리 이력이나 COMPOSER 상태로 추정하지 않는다.
- 현재 코드는 `getUpdates` 실패만 로그에 남기며, 성공을 김비서 상태나 성공 로그에 기록하지 않는다. 알림 전송 성공·실패 로그는 실제 알림이 발생했을 때의 기록이므로 유휴 시간의 연결 상태를 대신하지 못한다.
- 이번에는 요구사항만 기록하고 코드는 변경하지 않았다.

## EA 빌드 변경 후 녹화 호환성 확인

- 기존 창고의 XAUUSD+ 2026-09-01 하루 BAR 조각은 EA 해시 `af30fe4bf841bcbce9e99b1670d15452dd976fba090c075a66e09d9945c1ff32`, schema_id `933044592`였다. 수정본30 EA 해시 `e434827fdc453013a40942f55bd574bc6d2b35f38bdcd33fd8602bbec4eaab5c`로 같은 날을 `검증결과/ea_build_compat/day_probe/`에 별도 녹화했다. 기존 창고 조각은 덮어쓰지 않았다.
- 두 조각 모두 복원 묶음 **1,378개**, `bundle_sha256=d9c2868dff94ee621b97f8d4af82050f68c78b3a526ae50c48c7d93d984be493`이고 복원 검증을 통과했다. 비교 기록은 `검증결과/ea_build_compat/day_comparison.json`이다.
- 일치가 확인된 두 해시만 `Part2/ea_build_compatibility.json`에 수동 승인 목록으로 등록했다. 구축 계획과 재생 선택은 이 목록의 해시를 같은 빌드로 취급하며, 정확히 현 빌드 조각이 있으면 이를 우선한다. 호환 조각을 함께 써도 혼합 빌드 경고를 내지 않는다. 목록에 없는 빌드는 기존처럼 새 녹화 대상이다. 목록은 자동으로 확장하지 않는다.
- 실행 `result.json`에는 현재 EA 해시, 실제 사용한 조각별 EA 해시, 호환 적용 여부를 기록한다. 녹화 데이터의 실제 EA 해시 자체는 바꾸지 않았다.
- 회귀 시험 5개 통과. 실제 창고 메타데이터에 대한 읽기 전용 확인에서 기존 하루 조각 1개 재사용, 신규 녹화 0개, 누락 0개였다. 녹화 함수를 실패하도록 막은 상태에서도 준비가 완료되었다. 가짜 미등록 해시는 신규 녹화 조각 1개로 계획되었다. 정확히 현 빌드의 조각과 승인된 옛 빌드 조각이 둘 다 있을 때는 현 빌드를 우선한다. 이 확인 과정에서 텔레그램 전송은 없었다.
- 기존 창고의 같은 하루를 SPECIAL1 알림 전용으로 실제 실행했다. 구축 계획 0개 녹화·1개 재사용, 실행 ID `8d40ff6b73034749a27b4fbb56adea54`, 경과 18.55초였다. `result.json`에 옛 조각 해시와 현 EA 해시가 구분되어 기록되고 호환 적용이 `true`였다. 승인된 두 빌드에 대한 혼합 경고는 없었다. 결과 증거는 `검증결과/ea_build_compat/run_verification.json`이다.
- 첫 실행 시도 ID `1fdc912b636f4cf98d0a175cda65bd75`는 표준입력 스크립트가 Windows 자식 프로세스에서 재실행되지 못해 재생 시작 전에 실패했다. 파일 기반 검증 스크립트로 다시 실행해 위 결과를 얻었다. 실패한 실행 기록은 삭제하지 않았다.
- 이번 후속 작업의 수정 파일: `Part2/event_backtest/build_compat.py`, `build_plan.py`, `runner.py`, `Part2/ea_build_compatibility.json`, `tests/test_ea_build_compatibility.py`, 이 문서. 새 증거와 검증 스크립트만 `검증결과/ea_build_compat/`에 추가했다. 전략 판정 로직과 EA 코드는 변경하지 않았다.
