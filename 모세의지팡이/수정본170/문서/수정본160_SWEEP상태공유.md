# 수정본160: SWEEP 상태의 감시별 반복 계산을 한 번으로 (SWEEP·OZ 최적화)

수정본159를 별도 폴더로 복사해 작업했다. 이전 검증결과는 복사하지 않았다.

## 요청

사용자 결정(2026-10-08): "다음 수정본에서 스윕 올존 최적화하자." 159에서 9개 전략을 잰 결과, SPECIAL2에서 SWEEP 상태 2.85ms·OZ 상태 1.81ms(묶음당 14.7ms 중)였다.

## 원인 (SPECIAL2, 금 2026-09-16 하루)

SWEEP 처리기는 묶음마다 감시 24개 각각에 대해 같은 일을 되풀이했다.

| 반복 | 내용 |
|---|---|
| 시세판 보기 고르기 | 감시마다 시간봉 5개(`source_tf`, 1d, 4h, 8h, 5m)의 사용 가능·유효값 검사를 다시 함. 보기 객체 자체는 이미 게시 단위로 캐시돼 있었음 |
| 외부유동성 수준 | 감시마다 수준 캐시(`LevelStore.get`)가 닫힌 봉 배열을 다시 비교함. 같은 묶음 안에서는 입력이 같은 객체 |
| 수준 걸러내기 | 감시마다 같은 목록을 같은 선택자로 다시 거름 |
| 감시 설정 해석 | 묶음마다 `SweepSpec.from_payload`를 다시 함. 설정은 명령이 올 때만 바뀜 |
| 감지기 수준 동기화 | 묶음마다 수준 ID 집합과 상태 사전을 다시 만듦. 수준은 5분봉 마감 등 입력이 바뀔 때만 바뀜 |

## 바꾼 것

### `Part1/program/event_engine/sweep_runtime.py`

- **한 사건 안 공유**: 사건 하나는 시세판 게시 하나만 읽는다. 그래서 같은 종목 감시들은 같은 보기와 같은 외부유동성 수준을 쓴다.
  - 보기(`_view`)는 (종목, 시간봉)마다, 수준은 (종목, 런던 세션, 뉴욕 세션)마다 그 사건에서 한 번만 구한다.
  - 사건이 바뀌면(`bind`) 비운다. 상태 복사(`__deepcopy__`)에는 넣지 않는다.
- **걸러낸 목록 재사용**: `filter_external_levels`는 순수 함수이고, 수준 목록을 바꾸는 곳이 없다. `LevelStore`는 입력이 같으면 같은 목록 객체를 돌려준다. 그래서 (수준 키, 선택자)마다 같은 목록 객체면 걸러낸 결과를 다시 쓴다.
- **감지기 동기화 건너뛰기**: `_sync_levels`는 수준 ID만 읽고 상태 키를 바꾸는 유일한 곳이다. 그래서 직전과 ID 목록이 같으면 아무것도 바꾸지 않는다.
  - 목록 객체가 아니라 ID 목록으로 비교한다. 같은 목록을 제자리에서 고쳐 넘겨도 정확하다.
  - 상태 복원 때는 비교 기준을 비운다.

### `Part1/program/event_engine/sweep_state.py`

- **감시 설정 재사용**: 감시마다 설정 내용(리스트는 튜플로 바꾼 비교용 값)을 기억한다. 내용이 바뀔 때만 다시 해석한다.
  - 묶음 처리 중 `deepcopy`를 쓰지 않는다. 기존 시험이 이것을 막고 있다.

OZ는 바꾸지 않았다(아래 "OZ" 참고).

## 검증

### 로직 시험 (`tests/test_sweep_reuse160.py`, 4건)

| 확인 | 내용 |
|---|---|
| 공유 = 전체 계산 | 감시 5개(시간봉 1m·5m·15m·4h, 선택자·세션 설정이 서로 다름)로 90묶음을 돌렸다. 160 코드와 원래 계산(158 코드를 시험 안에 그대로 옮긴 참조)이 묶음마다 내보낸 사실·외부 이벤트·감지기 상태·지문·건강·수준 계산 횟수까지 같았다. 중간에 감시 교체(20묶음), 같은 설정 객체의 제자리 수정(35묶음), 감시 삭제·추가(50묶음)를 넣었다. 터치가 실제로 났고 수준도 다시 계산됐다 |
| 한 게시에 수준 계산 한 번 | 세션 설정 두 종류면 묶음당 두 번(감시 5개가 아님) |
| 설정이 바뀌면 다시 해석 | 안쪽 리스트를 제자리에서 바꿔도 다시 해석 |
| 동기화 건너뛰기 | 같은 ID, 같은 목록 객체에 ID 추가, 순서 변경, 삭제, 빈 목록에서 전체 동기화와 같은 결과 |

일부러 틀리게 고쳐서 시험이 잡는지도 확인했다. 확인 뒤 코드는 되돌렸다.
- 수준 공유 키에서 세션 설정을 빼면 2건 실패.
- 설정 기억을 같은 객체인지로만 판단하면 2건 실패.

## OZ: 고치지 않은 이유

py-spy 표본에서는 OZ 시간의 20~30%가 입력 비교(`same_feed`)·유효성 검사(`ready`)로 보였다. 처음에는 `same_feed`를 "마지막 행이 다르면 바로 다름"으로 바꿨다. 하지만 효과가 측정되지 않았다.

함수 시간을 직접 재니(`tools/ozparts160.py`, `tools/samefeed160.py`) 둘 다 작았다. py-spy가 작은 함수를 부풀려 보였던 것이다. 그래서 `same_feed` 변경은 되돌렸다. `oz_engine/runtime.py`는 159와 같다.

| 묶음당 ms | SPECIAL2 | SPECIAL1 | SPECIAL5 |
|---|---|---|---|
| OZ 전체 | 1.83 | 1.05 | 1.16 |
| OZ 판정 본체(`run_once`) | 1.37 | 0.70 | 0.80 |
| 감시 스냅숏(`snapshot_for_symbol`) | 0.35 (묶음당 6.9번) | 0.02 | 0.06 |
| 외부유동성 시장 갱신 | 0.26 | 0.00 | 0.01 |
| 유효성 검사(`ready`) | 0.06 | 0.16 | 0.15 |
| 입력 비교(`same_feed`) | 0.10 | 0.10 | 0.08 |

- OZ 시간의 70~75%는 시간봉마다 OZ를 실제로 판정하는 계산이다.
- BAR 녹화에서는 1분마다 모든 시간봉의 진행봉이 바뀐다. 그래서 매 묶음 모든 시간봉을 판정해야 한다.
- 반복으로 볼 만한 것은 SPECIAL2의 감시 스냅숏(0.35ms)뿐이다.
  - 같은 묶음 안에서도 OZ 완성 처리 사이에 감시가 지워지거나 외부유동성 상태가 바뀔 수 있다.
  - 그래서 공유하려면 모든 변경 경로가 판번호를 올린다는 것을 증명해야 한다.
  - 얻는 것은 SPECIAL2의 약 2%라 이번에는 하지 않았다.

OZ 외부유동성 상태 수는 한 달 동안 0~46개로 유지되고 쌓이지 않았다(`tools/states160.py`).
