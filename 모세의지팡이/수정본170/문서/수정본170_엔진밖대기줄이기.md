# 수정본170: 엔진 밖 대기 줄이기

수정본169를 복사해 만들었고, 169의 검증결과 폴더는 복사하지 않았습니다. 재생과 판단 로직, 실시간 감시(Part1) 동작은 바꾸지 않았습니다. 백테스트를 시작할 때, 창을 열 때, 결과 화면을 넘길 때 엔진 밖에서 기다리던 부분을 줄였습니다. 배포는 하지 않았습니다.

## 사용자 요청
- 백테스트 창과 설정 창이 한참 뒤에 뜨고, 시작 버튼을 눌러도 오래 기다린 뒤에야 진행됩니다. 엔진이 아닌 다른 병목을 찾아 보고하라는 요청이었습니다.
- 사용자가 먼저 찾은 병목은 다섯 가지입니다.
  - 라이브 화면의 반복 조회
  - RR·기간을 바꿀 때 분석 재계산
  - 거래내역 페이지마다 CSV를 처음부터 읽음
  - 목록이 폴더 전체를 탐색함
  - 설정의 전략 목록 반복 탐색
- 보고 뒤 지시는 "가 방식으로 하고 다음 수정본에서 진행해"였습니다.
  - 시작할 때 녹화 검사를 한 번만 하는 (가) 방식과 3~6번 항목을 170에서 합니다.
  - 가상진입 후처리(2번, SPECIAL8 60개월에 17.8분)는 171에서 합니다. 클로드코드 규칙은 그 뒤입니다.

## 1. 시작할 때 녹화 검사는 한 번 ((가) 방식)
**전:** 시작 한 번에 저장된 녹화 전체의 sha256을 4번 읽었습니다.
- 4번은 계획 단계(Part3가 띄우는 plan), 실행 단계의 계획, 녹화 준비(prepare)의 계획, 재생 직전(runner)입니다.
- 72개월이면 한 번에 292개 파일, 16.98GB를 읽고 약 15초가 걸립니다. 시작부터 첫 진행까지 약 62초 가운데 약 58초가 이 검사였습니다.

**지금:**
- 계획 단계는 목록(catalog), `complete.txt`, 파일이 있는지만 봅니다. 해시를 읽지 않습니다.
- 실행 단계가 재생 전에 한 번 해시합니다. 같은 실행 안의 prepare 계획과 runner는 그 결과를 씁니다.
- 계획 뒤에 녹화가 바뀌거나 망가지면 실행 단계의 계획이 달라집니다. 그러면 기존 "다시 확인" 흐름(`ConfirmationRequired`)으로 가고, 망가진 녹화는 재생하지 않습니다.
- 승인 토큰은 원래부터 재사용 녹화 목록(reuse)을 넣지 않습니다. 그래서 계획 단계의 해시를 빼도 토큰은 같습니다.
- runner를 다른 경로로 부르면(녹화 목록을 넘기지 않거나 검사했다고 알리지 않으면) 원래대로 해시합니다. 보유 확인 명령(`event_backtest missing`)도 원래대로 해시합니다.

## 2. 창고 정리는 작업을 만들 때 한 번
- **전:** 시작 한 번에 창고 정리(`cleanup_warehouse`)가 4번 돌았습니다. 작업을 만들 때(Part3), plan, run, run 안의 계획입니다. 연구소 작업 안에서는 그 작업 자신의 기록 때문에 뒤의 3번이 늘 "사용 중"으로 건너뛰어졌습니다.
- **지금:** Part3가 작업을 만들 때 한 번만 정리합니다. Part3가 띄우는 명령에는 `--skip-cleanup`이 붙습니다. 명령줄에서 직접 돌리면 원래대로 정리합니다.

## 3. 실행 뒤 analytics.json을 쓰지 않음
- **전:** 가상진입 실행이 끝나면 거래 CSV 전체를 다시 읽어 analytics.json을 썼습니다. 60개월 SPECIAL8 기준으로 105MB였고, 계산 5.6초와 쓰기 1.1초가 들었습니다. 그 뒤 result.json도 다시 썼습니다.
  - 결과 화면은 165부터 이 파일을 읽지 않습니다. 화면이 열릴 때 거래 CSV에서 바로 계산합니다.
- **지금:** analytics.json을 쓰지 않습니다. result.json은 한 번만 쓰입니다.
  - Part3는 분석 파일을 기다리지 않습니다.
  - 실행 중인 작업의 가상진입 결과는 169처럼 그 요청의 프로세스가 끝나면 엽니다. 기준 프레임 여러 개를 함께 시험하면 `run_many`가 실행을 하나씩(각자 가상진입 계산 뒤) 마무리하기 때문입니다(163). 먼저 끝난 실행을 다른 실행이 아직 계산 중일 때 미리 열지 않습니다. 이제는 분석 단계가 없으므로 프로세스는 마지막 결과를 쓴 뒤 곧바로 끝납니다.
  - 이미 있는 옛 analytics.json은 원본 파일로 그대로 둡니다.

## 4. job.json과 진행 기록
- job.json에 계획을 넣을 때 재사용 녹화는 `capture_id`·`start`·`end`만 남깁니다.
  - 화면, 승인, 진행이 쓰는 칸은 그대로입니다. 기록 단계, 변환, 예상 시간, 기간 조정, 승인 토큰이 여기에 들어갑니다.
  - 72개월 작업 기준 167kB에서 11.4kB가 됐습니다. 실행 중 감독 프로세스가 0.1초마다 읽는 파일입니다.
- 진행 값이 그대로면 job.json을 다시 쓰지 않습니다. 전에는 0.2초마다 다시 썼습니다. 끝 이벤트는 항상 씁니다.

## 5. 창 열기
- **설정 창 첫 열기:** 물리 코어 수를 PowerShell(WMI) 조회 대신 Windows에 직접 묻습니다(`GetLogicalProcessorInformationEx`).
  - 코어 수 조회는 1.3~1.5초에서 1ms 아래로 줄었습니다. 설정 창 첫 읽기 전체는 1,313ms에서 57ms가 됐습니다.
  - 값은 WMI와 같습니다(시험).
  - 묻지 못하면 논리 프로세서의 절반을 씁니다. 이것은 원래 실패할 때 쓰던 값과 같습니다.
- **백테스트 창 첫 열기(설정 목록):** pandas를 불러오지 않습니다.
  - Part2의 `base_frames`와 `virtual_contract`가 `indicator_facts`(pandas 사용) 대신 Part1 `command_interpreter`의 같은 함수(`tf_seconds`, `normalize_tf`)를 씁니다.
  - 모든 시간봉 입력에서 두 함수의 값이 같습니다(시험).
- **전략 목록:** 레지스트리가 전략 하나를 줄 때 목록 전체를 두 번 깊은 복사하던 것을, 그 전략 하나만 복사하게 바꿨습니다.
  - 내용은 같고, 복사본끼리 서로 독립입니다. 없는 전략의 오류 문구도 같습니다(169와 비교).
- 측정값은 아래 "측정" 표에 있습니다.

## 6. 결과 화면
- **거래내역 페이지:** 전에는 페이지마다 CSV를 처음부터 읽었습니다.
  - 이제는 같은 RR·기간이면 앞 페이지가 멈춘 곳부터 이어 읽고, 찾은 줄의 파일 위치를 기억합니다. 앞 페이지로 돌아가면 더 읽지 않습니다.
  - 따옴표로 묶인 줄바꿈이 줄 안에 있는 파일은 원래 방식(처음부터 읽기)을 씁니다.
  - 보이는 줄은 처음부터 읽은 것과 같습니다. 시험과 함께, 60개월 실제 거래 파일에서도 30가지 페이지를 비교했습니다.
- **RR 바꾸기:** 기간별 RR 표를 한 번만 계산하고, 같은 기간의 다른 RR에서 다시 씁니다. 돌려주는 표는 복사본입니다.
- **기간 바꾸기:**
  - 전에는 기본 RR로 전체 화면을 받은 뒤, 화면 정렬 기준의 1위 RR이 다르면 전체를 한 번 더 받았습니다.
  - 이제는 그 기간의 RR 표만 먼저 받고, 정렬 1위 RR로 전체 화면을 한 번 받습니다. 보이는 결과는 같습니다.

## 7. 라이브 화면 (연구소 화면만, Part1 감시는 그대로)
- 상태 조회는 한 번에 하나만 합니다. 응답을 기다리는 동안의 타이머(1.5초)는 건너뜁니다. 사용자가 바꾼 것은 응답 뒤 한 번 더 읽습니다.
- 로그 줄은 로그 화면이 열려 있을 때만 받습니다(`lines=false`).
- 모듈 카드는 모듈, 상태, 선택한 모듈이 바뀔 때만 다시 만듭니다.
