# 수정본129 최적화 2 — 녹화 파일 풀기

수정본128을 그대로 복사해(검증결과 제외) 수정본129를 만들었습니다. 백테스트가 녹화 파일에서 1분 묶음 원본을 되살리는 부분(`Part2/event_backtest/delta.py` `DeltaCodec`)을 줄였습니다. 백테스트 전용 코드이며, 되살리는 바이트는 그대로입니다. 무결성 검사(조각 CRC, 하루치 지문 SHA-256)는 사용자 결정대로 그대로 둡니다.

## 결과

| | 내용 |
|---|---|
| 되살린 바이트 동일성 (128 코덱과 나란히, 묶음마다 비교) | 9월 한 달 30,164묶음 — **차이 0** (CRC 검사 끔·켬 둘 다), 복원 지점(9/14)부터 읽기 17,912묶음 — **차이 0**. 제품의 하루치 지문 검사도 모두 통과 |
| 녹화 풀기 시간 (같은 묶음을 128·129에 번갈아, 한 달) | **63.8초 → 34.4초 (46% 감소)**. CRC 검사 켬: 141.0초 → 81.9초(42%), 복원 지점부터: 57.3초 → 27.7초(52%) |
| 실제 백테스트 (WATCH 명령 없음 · 1분 EMA 골크 WATCH 9건 · SPECIAL1) | 알림 128과 **모두 같음**, 자료 읽기 시간 17~24% 감소 |
| 기본 시험 | **3,035 passed · 0 failed** · 3 skipped · 2 xfailed |
| 통합설치 시험 | **440 passed** (UTF-8 모드) |

## 바뀐 것

수정본127 측정에서 녹화 풀기는 자료 읽기 시간의 약 31%였습니다. 이틀치 9.4초 중 마지막 줄 갱신 2.9초, 풀기 본체 4.9초, 하루치 지문 1.1초였습니다.

| 위치 | 변경 |
|---|---|
| `DeltaCodec.update` (ROW) | 이전: 마지막 줄만 바뀌어도 시간봉 배열(최대 650줄) 전체를 두 번 새로 만듦. 이후: 그 시각이 마지막 줄에만 있으면 그 자리에서 마지막 줄을 바꿈(배열은 코덱만 씀). 새 봉·중간에 같은 시각이 있는 경우 등은 원래 방식 |
| `DeltaCodec.decode` (한 줄 조각) | 한 줄짜리 ROW 조각은 넘파이 배열 준비 없이 그 줄만 복원 |
| `DeltaCodec.decode` (바이트 조립) | 조각마다 바이트를 이어 붙이고 다시 묶음으로 잇던 것을, 묶음 전체에서 한 번만 이어 붙임. CRC 검사를 켠 경우 같은 값을 조각별로 이어 계산 |

## 시험

새 시험 `tests/test_delta_decode129.py`:

- 마지막 줄 바꾸기(빠른 길), 새 봉, 처음 보는 시간봉의 ROW, 중간에 같은 시각이 있는 FULL 뒤의 ROW, 650줄에서 새 봉·마지막 줄 바꾸기, 하트비트를 섞은 묶음 열에서 되살린 바이트가 원본과 같고, 매 묶음 뒤 코덱 상태(인코더·디코더 모두)가 원래 규칙으로 새로 만든 배열과 같음 (CRC 검사 끔·켬)
- 앞서 되살린 묶음은 뒤의 갱신으로 바뀌지 않음
- CRC 검사를 켜면 한 줄 조각의 값이나 저장된 CRC가 깨졌을 때 거부
