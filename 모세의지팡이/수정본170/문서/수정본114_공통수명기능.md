새 스페셜과 Part3가 만드는 전략도 같은 선언으로 쓰는 공통 기능입니다. 스페셜 번호로 나뉘는 코드는 없습니다(`tests/test_recipe_contract114.py`가 소스를 검사합니다).

- `settings/strategy_registry.json`은 손으로 고치지 않았습니다. SPECIAL 폴더가 없는 옛 프로젝트에서만 읽는 읽기 전용 대체본이고(SPECIAL8이 없는 옛 7개 그대로), 배포본의 같은 파일은 빌더가 배포 때 SPECIAL 폴더에서 자동으로 만듭니다(`tests/test_release_lifecycle114.py`가 확인).
- ATR 기본값(14, 1.5)도 OZ 엔진(`oz_engine/common.py`)에 한 번만 정의하고 계약은 그 함수를 씁니다.

## 1. 외부유동성 연결 (`final.level_gate`)

```json
"steps": [{"kind": "EXTERNAL_LIQUIDITY_TOUCH", "tfs": ["1m"], "side": "LOW", "level": "ALL", "capture": "sweep"}],
"final": {"kind": "OZ", "tfs": ["SOURCE"], ..., "level_gate": {"ref": "sweep", "atr_period": 14, "atr_mult": 1.5}}
```

- 터치 단계의 `capture`가 실제로 선택된 레벨(코드·이름·가격·시각)을 기록합니다. 여러 레벨이 동시에 터치 상태면 알림 위치와 같은 규칙(LONG 최저가, SHORT 최고가, 같으면 최근 터치)으로 하나를 고릅니다.
- 최종 OZ 감시(`MANUAL_WATCH`)에 `external_watch_id`·`external_source_tf`·`external_liquidity_required`와 선택 레벨이 실립니다. 판정은 **OZ 엔진의 기존 외부유동성 Gate**가 합니다: 1차(터치 봉이 레벨에서 ATR×배수 넘게 벗어남), 생존(터치 이후 극값), 최종(OZ 저점·고점과 레벨의 거리). 같은 계산을 포트에 다시 만들지 않았습니다.
- ATR 기간·배수는 전략이 정합니다. SWEEP_WATCH 페이로드의 `external_atr_period`/`external_atr_mult`로 OZ 엔진 spec에 들어가며, 없으면 기존 ATR14×1.5입니다. 기간이 14가 아니면 `parameterized_atr_fact`와 같은 정의(`true_range_array` + `rma_array`)를 OZ 시장 뷰의 이름 붙은 OZ Fact(`atr_series`)로 계산합니다.
- 최종 OZ 시간봉은 터치와 같은 `SOURCE`여야 합니다(OZ 엔진 Gate가 원천 시간봉에서만 2차 검사를 하기 때문). 계약이 거부합니다.
- 규칙이 다른 두 터치는 서로 다른 SWEEP watch입니다(watch id에 규칙이 들어갑니다). 규칙을 선언하지 않은 전략의 watch id는 그대로입니다.
- 수정본114의 실제 터치 이름·가격 표시(`• 위치: 전일 저가 · 3,842.15`)는 유지합니다.

검증: `tests/test_level_link114.py`(연결 필드), `tests/test_level_gate114.py`(ATR 정의·허용 거리 경계·체크포인트·Recipe 명령이 OZ 엔진에 들어가 통과/탈락), `tests/test_special2_engine114.py`(실제 엔진, LIVE·백테스트 동일).

## 2. 대기시간

| 이름 | 뜻 |
|---|---|
| `within_sec` | 조건끼리 허용하는 시간(처음 조건부터 마지막 조건까지) |
| `final_window_sec` / `lifecycle.expires.seconds` | 조건이 갖춰진 뒤 최종 OZ를 기다리는 시간 |
| `final_window_from` | 최종 대기를 세기 시작하는 때: `ALL_CONDITIONS`(기본, 모두 모인 때) / `FIRST_CONDITION`(처음 조건이 발생한 때) |

- 시작 사건의 시각은 그 사건이 발생한 시각(예: 30분봉 시작 시각)이고, 처음 본 시각이 아닙니다.
- 처음 조건부터 세면 마지막 조건이 올 때 이미 대기가 끝났을 수 있습니다. 그때는 감시를 열지 않습니다.
- `final_window_sec`는 끝나는 순간까지 받아들이고, 수명 `seconds`는 그 순간에 끝납니다(기존 그대로).

### SPECIAL3: 수정본50과 현재의 실제 계산 대조

수정본50 `event_composer_domain.py` L5493~5498(순서무관 쌍)·L6005(FVG 터치)·L5174(최종 OZ)의 계산:
`기한 D = min(쌍 완성 + final_window_sec, 처음 사건 + max_gap_sec)`. FVG 터치와 최종 OZ 완성 시각이 둘 다 `D`를 넘으면(`>`) 탈락합니다.
현재 `SPECIAL3.recipe.json`: `within_sec 1800`, `final_window_sec 7200`, `final_window_from` 선언 없음(= 모두 모인 때). 대기 종료는 `둘째 조건 + 7200초`입니다.

처음 조건 09:00:00 기준(`tests/test_wait_time114.py`의 실제 상태머신 계산):

| 둘째 조건 | 수정본50 기한 | 현재 기한 | 현재가 더 긴 시간 | `final_window_sec 1800` + `FIRST_CONDITION` |
|---|---|---|---|---|
| 09:00:00 | 09:30:00 | 11:00:00 | 90분 | 09:30:00 (같음) |
| 09:10:00 | 09:30:00 | 11:10:00 | 100분 | 09:30:00 (같음) |
| 09:29:59 | 09:30:00 | 11:29:59 | 약 120분 | 09:30:00 (같음) |
| 09:30:00 | 09:30:00 | 11:30:00 | 120분 | 09:30:00 (같음) |
| 09:30:01 이후 | 시작 안 함 | 시작 안 함 | 같음 | 시작 안 함 |

차이 정리:

1. 기한: 수정본50은 간격 1800이 항상 먼저 닿아 `처음 사건 + 1800초`였고 7200은 쓰이지 않았습니다. 현재는 `둘째 조건 + 7200초`입니다.
2. FVG 터치: 수정본50은 터치도 `D` 안에 와야 했습니다. 현재는 `둘째 조건 + 7200초` 안이면 됩니다.
3. 판정 시각: 수정본50은 사건 시각(쌍 완성·OZ 완성 시각), 현재는 평가 시점의 보드 시각입니다.
4. 같은 것: 조건 간 허용 1800초(경계 포함), 최종 대기의 마지막 순간 포함.

적용할 설정(제가 정하지 않았고 SPECIAL3 값은 바꾸지 않았습니다): 수정본50과 같게 하려면 `final_window_sec`를 1800으로, `final_window_from`을 `FIRST_CONDITION`으로 선언합니다. `final_window_sec`가 `within_sec`보다 작으면 수정본50의 `min()`을 한 값으로 쓸 수 없어(`complete + W`가 먼저 닿는 경우) 정확히 같아지지 않습니다. SPECIAL3은 W 7200 ≥ G 1800이라 해당하지 않습니다.

## 3. 봉 수 만료 (`lifecycle.expires`)

- `{"bars": 10, "bars_setting": "MAX_BARS_AFTER_B0", "tf": "FINAL"}`: 설정(config) 값이 양의 정수면 그 값, 없거나 잘못되면 `bars`가 한도입니다. 확정봉 수가 한도를 **넘으면**(`>`, `>=` 아님) 종료합니다.
- `MAX_BARS_AFTER_B0`: OZ 엔진(`oz_engine/profile.py`)의 후보 타이머 설정(기본 10)이고, 수정본50 SPECIAL5가 하위 감시 만료 한도로도 같은 설정을 읽었습니다(`bars > 설정`, setup 이후 하위 TF 확정봉 수).
- SPECIAL5는 `bars: 1` 고정을 이 선언으로 바꿨습니다.
- 하위 프레임별 계산(1m·2m·3m 각자 자기 봉)과 부모·하위 반대 교차 취소는 유지했습니다(`tests/test_special5_lifecycle114.py`).
- 찾아서 고친 결함: 부모 TF 반대 HMA 교차가 같은 부모의 자식 중 **먼저 평가된 하나만** 취소했습니다. SOURCE/FINAL에 묶인 조건의 직전 봉 기준값이 머신끼리 공유됐기 때문입니다. 묶인 조건은 머신별로 보관합니다(묶이지 않은 조건은 그대로).

## 4. 선행 조건 검사 방식 (`lifecycle.precondition_check`)

- `WHILE_ACTIVE`(기본·기존 동작): 감시하는 동안 상태 조건을 계속 검사하고, 거짓이면 취소하며 최종도 막습니다. 값이 아직 없으면(미준비) 최종을 보류합니다.
- `AT_START`: 감시를 시작할 때만 검사합니다. 이후 거짓이어도 취소·차단하지 않고, 미준비도 막지 않습니다. 시작할 때 거짓이면 시작하지 않습니다.
- 사건 조건·취소 조건·최종 조건은 이 선택과 무관합니다. SPECIAL1·5·6·7은 선언하지 않아 기본값입니다(시험으로 확인).

## 5. SPECIAL4 검증 결과 (`tests/test_special4_lifecycle114.py`, `tests/test_special4_engine114.py`)

| 확인 | 결과 |
|---|---|
| 30분 마감에서 시작 | 첫 발행이 경계보다 늦으면(0.3초만 늦어도) **시작하지 않았음 → 수정** |
| 확정봉 기준 가격·ATR 저장 | 문제 없음: 경계 직전 확정 30분봉 종가, 경계 직전 확정 1분봉 ATR14 |
| 6분 만료 | 폴링 시각부터 셌음 → 30분 마감 시각부터 세도록 수정(359초 생존, 360초 종료) |
| ATR 1배 선행이동 | 창이 폴링 시각에서 시작해 경계 봉의 극값이 빠졌음 → 경계 봉부터 포함하도록 수정(`>=` 경계: 한도 −0.01은 유지, 한도 이상은 취소) |

원인과 수정:
- 시작 실패: `restart_on` 재시작이 새 활성화의 기준을 "지금"으로 잡아, 같은 봉의 BAR_CLOSE 사건(발생 시각 = 30분 경계)을 이미 지난 사건으로 버렸습니다. 재시작을 일으킨 사건의 시각을 기준으로 넘기도록 고쳤습니다(`replace`로 시작하는 경우도 같음).
- 만료: SPECIAL4.recipe.json에 `final_window_from: FIRST_CONDITION`을 선언했습니다.
- 선행이동 창: 스냅샷을 잡은 봉 경계 시각을 보관해 거기서부터 극값을 봅니다.
- 한계: 선행이동 검사는 활성화한 폴링의 다음 평가부터입니다. 최종 OZ 이벤트는 자기 폴링을 먼저 하므로 그 사이에 알림이 나가지 않습니다.
