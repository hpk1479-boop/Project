# 수정본153: 가상진입 병목 개선 (기록 풀기 개선, 코어 분할)

수정본152를 별도 폴더로 복사해 작업했다. 이전 검증결과는 복사하지 않았다.

## 요청

- 가상진입 병목을 개선한다. 지금은 코어 1개로 직렬이고, 160만 개를 복원해 53만 개만 쓴다.
- 코드를 고치기 전에 영향 받는 파일과 데이터 흐름부터 보고한다.
- 창고는 모세트레이딩시스템\데이터창고 하나만 쓴다. 측정은 그 창고의 녹화를 임시 폴더로 복사해서 했고, 창고에는 아무것도 쓰지 않았다.

## 1. 고치기 전 측정 (152와 같은 코드)

금 2026-09-07 ~ 10-01, SPECIAL8, 실제 프로그램과 같은 경로(14코어 재생 → 가상진입)로 쟀다.

| | 기준 1분 | 기준 1시간 |
|---|---|---|
| 가상진입 | 7.4초 | 5.7초 |
| 알림 | 725 | 12 |
| 복원한 기록 → 판정에 쓴 관측 | 24,653 → 7,679 | 18,636 → 8,044 |
| 녹화 다시 읽기 | 78% | 97% |
| └ 기록 풀기 (`Projection.decode`) | 4.10초 | 4.26초 |
| 진입 판정·손익 | 20% | 2% |

- 시간 대부분이 녹화를 코어 1개로 한 번 더 읽는 일이었다.
- 기록 하나에 시간봉 feed가 19개 들어 있다. 필요한 것은 1~2개인데, 19개를 모두 파이썬으로 하나씩 해석했다.
- 관측마다 진행 중인 알림은 평균 1.0~1.1개였다. 알림이 많아서 느린 것이 아니다.

기록: `검증결과/revision153/measurement/run_special8_*.json`, `profile_*_split.json`, `profile_1h_cprofile.json`

## 2. 바꾼 것

### 기록 풀기 (`virtual_msd.py`)

- 기록을 스트림이 아니라 위치(offset)로 읽는다. 가상진입이 읽지 않는 feed는 길이만 읽고 건너뛴다. 잘린 기록, 남는 바이트, 지원하지 않는 종류는 전처럼 ValueError로 거부한다.
- 고른 feed의 열 고르기를 열마다 도는 반복에서 한 번의 표 찾기로 바꿨다.
- ROW가 마지막 봉만 바꿀 때는 창을 다시 이어 붙이지 않고 마지막 줄만 바꾼다. 결과는 일반 경로와 같다.

### 코어 분할 (`virtual_entry.py`, `runner.py`)

- 알림을 UTC 날짜 단위로 나눠 연속된 묶음을 만든다. 날짜는 녹화의 복원 단위다. 작업자 1개당 묶음을 약 2개 만든다.
- 묶음마다 작업자 프로세스가 자기 첫 날부터 녹화를 읽는다. 거래가 끝날 때까지 다음 날로 넘어가며 읽는다.
- 메인은 결과를 알림 순서대로 합친다.
- 작업자 수는 재생과 같다. 직렬 실행(`sequential`)이면 1이다.
- 작업자가 1이거나 알림이 하루치뿐이면 프로세스를 띄우지 않는다. 이때는 이전 코드와 같은 반복을 한 프로세스에서 돈다.

결과가 같아야 하는 근거:
- 알림마다 따로 `VirtualEntry`를 만든다. 알림끼리 공유하는 것은 순수 캐시(`VirtualFacts`)뿐이다.
- 하루 시작점(seed)은 인코더의 연속 상태를 그대로 담는다(`keyframes.full_bootstrap`). 그래서 어느 날부터 읽어도 그 시각의 창이 같다.

중단·오류·진행률:
- 중단하면 메인이 실행 폴더에 `stop.request`를 만든다. 작업자는 0.5초마다 이 파일을 확인한다. 시작하지 않은 묶음은 취소하고, 결과는 부분 결과로 남는다.
- 작업자 오류는 모든 묶음이 끝난 뒤 가장 앞 묶음의 오류를 낸다. 같은 입력이면 같은 오류다.
- 진행률(`VIRTUAL_ENTRY_PROGRESS`)은 묶음별 `progress.json`을 메인이 합쳐서 보낸다. 화면이 쓰는 칸(percent, processed_alerts, total_alerts, elapsed_seconds)은 그대로다.

## 3. 검증

### 로직 시험 (`tests/test_virtual_parallel153.py`, 28개 통과)

| 확인 | 내용 |
|---|---|
| 기록 풀기 = 무손실 상태 | 무작위 1m·5m·1h 기록 18가지(FULL 3~650봉, ROW, APPEND, HEARTBEAT, NaN·inf·1e301·-0 비트). 고른 feed의 창이 DeltaCodec 상태와 비트 단위로 같고, 고르지 않은 feed는 상태에 없음 |
| 잘린·남는 기록 | 여러 위치에서 자른 기록, 바이트 추가, 값 부족·초과를 모두 ValueError로 거부 |
| 묶음 나누기 | 하루가 두 묶음에 걸치지 않음, 빈 묶음 없음, 작업자 1개나 하루치면 1묶음 |
| 묶음 = 한 줄 읽기 | 사흘짜리 MSD2 녹화(1m APPEND·ROW, 읽지 않는 5m), 알림 24개(같은 분 2개, 날 끝 알림 포함), SPECIAL8 레시피 진입과 즉시 진입. 작업자 2개(3묶음)와 1개의 거래·요약 CSV가 같음. 다음 날 묶음까지 이어진 거래가 들어 있음 |
| 중단 | 부분 결과·중단 표시·`stop.request` |
| 오류 | 녹화에 없는 시간봉이면 작업자 1개와 여러 개가 같은 오류 |

## 4. 이전과 달라진 것

| 차이 | 판단 |
|---|---|
| 거래·요약 결과 | 달라진 것 없음 |
| `read_bundles`, `reader_metrics` | 묶음별 값을 더한다. 겹쳐 읽은 날은 두 번 센다. 결과가 아니라 일한 양이다 |
| 결과에 `alert_groups`(묶음 수) 추가 | 진단용 |
| 실행 폴더에 `virtual_entry/group_NNN/progress.json` 생김 | 창고 정리는 실행 폴더를 지우지 않고 그 안을 검사하지 않는다 |
| 여러 묶음일 때 진행 이벤트에 `time_ms` 없음 | 화면은 이 칸을 쓰지 않는다 |
| 중단 시 부분 결과 | 직렬은 앞 알림부터 처리된 만큼, 여러 묶음은 묶음마다 처리된 만큼 남는다. 둘 다 중단 결과로 표시된다 |

## 5. 하지 않은 것과 남은 일

- **기준 1분 판정 개선(pandas 표 다시 만들기)**: 하지 않았다. 코어 분할 뒤 가상진입이 전체의 3~4%라서 줄여도 전체 시간에 거의 영향이 없다.
- **복원 비율(복원한 기록 / 판정에 쓴 관측, 2~3배)**: 그대로다. 하루 안에 시작점을 더 두려면 녹화 형식을 바꾸고 재구축해야 해서 하지 않았다. 대신 기록 하나를 푸는 비용을 줄이고 여러 코어로 나눴다.
- 이제 남은 시간은 대부분 재생이다(3개월 기준 86~90초).
- `verification/test_backtest_auto78.py`(16건)와 `test_release_watch95.py`(58건)는 152에서도 같은 74건이 실패한다. 138에서 없앤 작업 구간 "자동"(`requested_work_size`)을 아직 기대하는 옛 시험이다. 이번에는 고치지 않았다.
