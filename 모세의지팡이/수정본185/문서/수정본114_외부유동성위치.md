# 수정본114 SPECIAL2 알림 위치: 실제 터치된 외부유동성 표시

SPECIAL2 알림의 위치 줄이 `1분 하단 외부유동성 ALL 터치`로 나오던 문제를 고쳤습니다. `ALL`은 Recipe가 선언한 선택자일 뿐이어서, 알림에는 실제로 터치된 레벨의 이름과 가격을 보여줍니다.

```text
• 위치: 전일 저가 · 3,842.15
• 위치: 4시간 고가 · 25,941.30
```

## 바꾼 곳 (공용 Recipe 런타임, 표시 경로만)

- `Part1/program/strategy_recipe/port.py`: `EXTERNAL_LIQUIDITY_TOUCH` 관측에서 이미 판정에 쓰던 `hits`(SWEEP Fact)의 `level_code`, `level_name`, `level_price`, 터치 시각을 `touched_levels`로 observation에 실었습니다. `hits`, `matched`, `token`, `at` 계산은 그대로입니다.
- `Part1/program/strategy_recipe/alerts.py`: observation이 성립(matched)이고 부정 조건이 아니면 `touched_levels`의 대표 레벨을 `이름 · 가격`으로 표시합니다. 위치 줄에는 TF 접두어를 붙이지 않습니다(주기는 `• 주기:` 줄에 있습니다).
- `tests/test_external_level_display114.py`: 새 regression test 15건.

SPECIAL2 전용 코드는 없습니다. `EXTERNAL_LIQUIDITY_TOUCH`를 쓰는 모든 Recipe에 공통 적용됩니다. Part2도 같은 `strategy_recipe`를 쓰므로 같은 문구가 나옵니다.

## 표시명

| 코드 | 표시 |
|---|---|
| PDH / PDL | 전일 고가 / 전일 저가 |
| PWH / PWL | 전주 고가 / 전주 저가 |
| PREV_4H_HIGH / LOW | 4시간 고가 / 4시간 저가 |
| PREV_8H_HIGH / LOW | 8시간 고가 / 8시간 저가 |
| PREV_SESSION_HIGH / LOW | SWEEP Fact가 이미 갖고 있는 이름(`이전 세션 고가/저가`) 그대로 |
| 그 밖의 코드 | Fact의 `level_name`, 없으면 코드 |

여러 레벨이 동시에 터치 상태면 기존 외부유동성 Gate의 대표 규칙과 같이 방향별 최외곽(LONG은 최저가, SHORT는 최고가, 같으면 가장 최근 터치)을 보여줍니다.

## 바꾸지 않은 것

- `SPECIAL2.recipe.json`: 수정본113과 해시가 같습니다(`level: "ALL"` 유지).
- 진입 판정, 상태머신, 조건 순서, 신호 발생 조건, SWEEP 판정 로직.
- 실제 터치 정보가 없는 경우의 폴백: 명시 레벨(`PDL`, `PDL/4H` 등)은 기존 문구 그대로이고, 선택자 `ALL`만 문구에서 뺍니다(`1분 하단 외부유동성 터치`).

## 검증

- `tests/test_external_level_display114.py` + `tests/test_recipe_alerts101.py` + `tests/test_recipe_alerts112.py`: 48개 통과 (`검증결과/revision114/pytest_external_level_display.txt`).
- 새 테스트는 실제 `SPECIAL2.recipe.json`을 `execution_plan`으로 풀고, 실제 `IntentPort.observe`에 SWEEP Fact를 주입한 뒤 `render_strategy_alert`까지 확인합니다. 발생해야 할 입력(LONG/SHORT 각 레벨), 발생하면 안 되는 입력(다른 방향, 선택되지 않은 레벨, 빈 Fact), 부정 조건, 다중 터치를 시험했습니다.
- 수정본113 대비 바뀐 파일은 위 3개뿐입니다.

## 낡은 테스트 수정

두 테스트는 이번 변경과 무관하게 수정본113에서도 실패하던 것입니다(113에서 읽기 전용으로 확인). 로직이 아니라 테스트 가정이 낡아서 고쳤습니다.

- `tests/test_notifications_release112.py`, `tests/test_entry_release113.py`: 앱 리비전을 `112`, `113`으로 고정해 두었는데 리비전은 수정본 폴더 이름에서 오므로 114에서는 항상 실패합니다. 고정값 대신 "양의 정수"인지만 probe에서 보고, 개발 폴더의 리비전이 폴더 번호(`수정본N`)와 같은지는 본문에서 비교합니다. 이동·설치본이 같은 번호를 유지하는지는 기존 `developer == installed == moved` 비교가 그대로 확인합니다.
- `tests/test_notifications_release112.py`: 내장 전략이 SPECIAL1~7(모두 OZ 최종)이라고 가정했지만, 현재 `SPECIAL8`(최종이 NOTIFY라 `validation_mode` 없음)이 있어 KeyError가 났습니다. `validation_mode`/`trigger_mode`를 `.get`으로 읽고, 기대 ID는 `Part1/program/SPECIAL/SPECIAL*.recipe.json` 파일 목록으로 바꿨습니다. 전략이 더 추가돼도 번호 고정 때문에 깨지지 않습니다.
- 검증: 두 파일 9개 통과 (`검증결과/revision114/pytest_release_revision_tests.txt`). 소스 없는 배포본으로 옮긴 뒤에도 같은 결과입니다.

## 확인하지 못한 것

- 실데이터 LIVE 알림이나 장기 백테스트는 돌리지 않았습니다(합성 Fact 입력 기준).
- 프로젝트 전체 테스트는 돌리지 않았습니다. 위 두 번호 고정 테스트 외에 `수정본N` 번호를 고정한 Part1/Part2 테스트는 `tests/`에서 더 찾지 못했습니다.
- Part3는 규칙에 따라 검증에서 제외했습니다. `Part3/tests/test_app_version112.py`도 112를 고정하는 것으로 보이지만 열어 수정하지 않았습니다.
