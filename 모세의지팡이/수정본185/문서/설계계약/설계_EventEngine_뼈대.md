# Event Engine 뼈대 설계 (수정본15 = S8 완료본 기준)

목표는 세 가지입니다.

1. 원하는 조건을 하나도 놓치지 않는다.
2. 오늘 LIVE를 내일 백테스트로 재현한다(같은 엔진·같은 코드, 대조 기준은 텔레그램 알림).
3. 새 조건을 빠르게 백테스트한다.

LIVE와 BACKTEST는 **같은 엔진, 같은 코드**를 쓴다. 차이는 이벤트가 파이프에서 오느냐 데스크톱 과거 데이터에서 오느냐뿐이다.

**LIVE 검증 기준은 텔레그램 알림이다.** 노트북에 별도 영구 기록(Journal)을 두지 않는다. 같은 기간을 데스크톱 백테스트로 돌려 텔레그램에 온 알림과 비교한다.

> 개정 (2026-09-26): 노트북 Journal·감사 재생·영구 Outbox를 제거했다(텔레그램 알림이 LIVE 기록 역할). 그 외 반영 사항: Ingress Sequencer 순번 할당, 무손실 보장 범위와 EA 관측 주기, BUNDLE 원자 적용, signal_id, seq와 시각의 분리, Fact와 상태 처리기 구분, 스케줄러와 같은 시각 순서 규칙, DEGRADED 처리, 종목별 병렬과 체크포인트, 구현 위치 고정, 섀도 모드.

## 1. 전체 구조

```
MT5 EA ─(Wire v2: FULL/ROW/HB, TF BUNDLE, source_seq)─▶ STAFF: 수신·검증·불변 Snapshot (계산 없음)
                                                         │  이벤트로 변환
                                                         ▼
                          Ingress Sequencer: engine_seq 할당 (모든 입력의 단일 관문, 메모리)
                                                         │
                                                         ▼
                          Event Engine: 단일 스레드 처리 루프, Scheduler 내장
                                                         │
                                                         ▼
                          Pure Fact DAG: 계산값 (ATR, HMA 기울기, 퍼센타일 위치, regime 위치)
                                                         │
                                                         ▼
                          Stateful Processor: 이벤트 순서에 따라 변하는 상태
                                           (OZ 후보/B0/트리거 누적, FVG 활성/채움/만료, SWEEP 상태)
                                                         │
                                                         ▼
                          전광판(Board): MT5 입력값 + Fact + 처리기 상태, 읽기 전용, 이벤트 시점 고정
                                                         │
                          Consumer(Strategy): INDICATOR · Watch · SPECIAL1~7 · OZ/FVG/SWEEP 알림
                                                         │  SIGNAL
                                                         ▼
                          Output: 김매니저(문구·수신자·signal_id 중복 방지) → 텔레그램
```

**구현 위치 (고정)**

```
Part1: Event Engine · Scheduler · Board · Fact DAG · Stateful Processors · Strategies · Output
Part2: 데스크톱 MT5 과거 데이터 추출 → DuckDB 적재 · 과거 이벤트 공급기 → Part1 Event Engine을 가져다 씀
```

Part1은 끝까지 Part2를 모른다. Part2가 Part1 엔진을 사용한다.

## 2. 이벤트

모든 이벤트는 불변 객체이며 다음 공통 필드를 갖는다.

| 필드 | 의미 |
|---|---|
| `engine_seq` | 엔진 전역 순번. 처리 순서 자체 |
| `engine_time` | 엔진이 이벤트를 받은 시각 (지연 측정용, 판단에는 쓰지 않음) |
| `source` | 발생원 (심볼별 MT5 피드, telegram, gemini, scheduler, engine) |
| `source_seq` | 발생원이 가진 순번 (예: Wire v2 seq). 누락 감지는 이 값으로만 한다 |
| `source_time` | 발생원 기준 시각 (MT5 관측 시각 등). **판단에 쓰는 유일한 시계** |
| `kind` | 아래 종류 중 하나 |
| `payload` | 종류별 내용 (불변) |

- 엔진 처리 순서(`engine_seq`)와 MT5 누락 감지(`source_seq`)는 섞지 않는다.

**이벤트 종류 (최소 집합)**

| kind | 발생원 | 내용 |
|---|---|---|
| `MARKET_BUNDLE` | STAFF | 한 심볼의 같은 관측 회차에서 바뀐 TF Snapshot 묶음 (Wire v2 BUNDLE 그대로) |
| `FEED_GAP` | STAFF | source_seq 누락 범위 (S6 `staff-seq-gap/v1` 기록을 그대로 이벤트로 사용) |
| `FEED_HEALTH` | STAFF | FRESH/STALE/UNAVAILABLE 전이, 재연결 |
| `TIMER` | Scheduler | 전략이 요청한 시각 도달 (쿨다운 만료, N초 뒤 확인 등) |
| `COMMAND` | 텔레그램 | 사용자 명령 원문, chat_id, 수신 시각 |
| `EXTERNAL_REPLY` | Gemini 등 | 외부 응답 원문 (명령 해석 결과 포함) |
| `CONFIG` | 시작 시 | config 값 (σ, 대상 심볼 등). 실행 중 변경 없음 |
| `SIGNAL` | 전략 | 전략이 낸 신호. Output의 입력 |
| `STRATEGY_ERROR` | 엔진 | 전략 예외 (전략 이름, 실패 engine_seq, 예외 요약). 로그 파일에 남긴다 |

## 3. 처리 규칙 (재현성의 핵심)

1. **순번 할당 → 적재:** 수신 → 검증 → **Ingress Sequencer가 `engine_seq` 할당** → 큐 → 엔진 처리 순서다.
   - STAFF, 텔레그램, Gemini, Scheduler 등 모든 입력은 Ingress Sequencer 하나만 거친다. 엔진은 순번을 새로 매기지 않는다.
   - 영구 기록은 하지 않는다. 프로그램이 죽으면 큐에 있던 수 초 분량은 잃을 수 있으며, 이는 허용한다(재시작 후 MT5 FULL로 상태 복구).
2. **단일 처리 루프:** 이벤트는 엔진 큐에서 하나씩 순서대로 처리한다. 전략별 스레드와 폴링 루프는 없다.
3. **순서 규칙:**
   - 큐에 들어온 순서가 곧 `engine_seq`다. LIVE에서는 도착 순서, 백테스트에서는 과거 데이터의 시각 순서다.
   - 같은 시각의 여러 심볼 묶음은 도착 순서 그대로 처리하며, 심볼 이름순으로 다시 정렬하지 않는다.
   - **같은 시각의 MARKET_BUNDLE과 TIMER는 MARKET_BUNDLE을 먼저 처리한다.** 이 규칙은 영구히 고정한다.
   - 같은 이벤트 안에서의 실행 순서는 Pure Fact → Stateful Processor → Consumer(등록 순서)로 고정한다.
   - **MARKET_BUNDLE은 Board의 원자적 트랜잭션 하나다:** 묶음 안의 모든 TF를 Board에 적용 → 한 번에 commit → Fact 무효화 → Stateful Processor → Consumer 순으로 처리한다. TF 하나 적용할 때마다 전략을 돌리는 방식(1m 적용 → 실행 → 5m 적용 → 실행)은 금지한다. 전략이 1m은 새 시점, 15m은 이전 시점인 혼합 Snapshot을 보면 안 된다.
   - 트랜잭션 단위는 심볼별 묶음 하나다. 다른 심볼의 묶음은 별도 트랜잭션이며 도착 순서대로 처리한다.
4. **시계:** Fact·처리기·전략은 `source_time`만 쓴다. `time.time()`, `datetime.now()`, `monotonic()` 직접 호출은 금지한다(정적 검사로 막는다). 지연 측정만 예외다(Scheduler도 `source_time`만 쓴다).
5. **무작위·외부:** 무작위 값은 쓰지 않는다. 외부 응답(Gemini, 텔레그램 입력)은 이벤트로 들어온 것만 쓴다. 전략이 직접 네트워크를 호출하지 않는다.
6. **절대 버리지 않음:** 큐는 버리거나 합치지 않는다(coalescing 금지). 밀리면 지연만 허용한다. 큐 길이와 처리 지연을 계측하고, 임계를 넘으면 경고 이벤트를 남긴다.
   - **보장 범위:** 엔진의 무손실 보장은 **STAFF까지 도착한 이벤트**에 한한다. EA가 관측하지 않은 순간(예: 00.300 발생, 00.600 해제, 사이에 전송 없음)은 엔진이 알 수 없다.
   - **LIVE 입력 규칙 (확정 방향):**
     ① EA는 매 틱 관측한다(OnTick).
     ② 변경분만 보낸다. 가격이 바뀐 틱마다 진행 봉이 바뀐 TF의 마지막 한 줄(ROW)만 보낸다. 가격 변화가 없는 틱은 보내지 않는다.
     ③ 한 틱의 모든 TF 변경분을 하나의 BUNDLE, 하나의 `source_seq`로 묶는다. `source_time`은 틱 시각(밀리초)이다.
     ④ 엔진은 하나도 버리지 않는다. EA에서도 최소 간격 같은 틱 합치기는 하지 않는다.
   - 대가는 지연이다. 묶음 1개 평균 처리 시간이 평균 틱 간격보다 짧아야 한다. **묶음 1개 처리 시간을 뼈대 단계의 핵심 측정값으로 한다.** 뉴스 때 일시적 적체는 허용하고, 큐 길이·지연 경고로 감시한다.
   - 적용 시점은 S8 결과(EA 부하)를 보고 확정한다.
7. **순서가 보장된 자료구조만:** 상태와 출력은 set/dict 순서에 의존하지 않는다. 출력 목록은 정렬 키를 명시한다.
8. **오류 격리:** 10장 3번을 따른다.

## 4. Pure Fact, Stateful Processor, 전광판

**Pure Fact**
- 입력이 같으면 결과가 같은 계산값이다. 예: ATR14_GENERAL, HMA 기울기, 퍼센타일 위치, regime 위치.
- **Fact 등록부 하나:** `indicator_facts`의 `fact()` 등록부를 확장해 모든 공용 Fact를 여기에 둔다.
- 전략 내부 Fact(예: FVG_WILDER_ATR)는 해당 전략 모듈에만 둔다.
- **정의 필드:** 이름, 입력 의존(MT5 열 또는 다른 Fact), 주인 모듈, 계산 함수, 무효화 단위(봉 확정 시 / 진행 봉 변경 시).
- **무효화:** `MARKET_BUNDLE`이 바꾼 (심볼, TF)의 입력에 의존하는 Fact만 다시 계산한다. 같은 이벤트 안에서는 한 번만 계산해 모두가 공유한다.

**Stateful Processor**
- 이벤트 순서에 따라 변하는 공용 상태다. 예: OZ 후보/B0/트리거 누적, FVG 활성/채움/만료, SWEEP 상태.
- Fact DAG에 넣지 않는다. 입력은 Board의 MT5 값과 Pure Fact이고, 출력은 Board에 읽기 전용 상태로 올린다.
- 상태는 엔진이 소유하고 체크포인트에 포함된다.
- 여러 Consumer가 같은 상태를 쓰면 처리기는 하나만 두고 공유한다(중복 계산 금지).

**공통**
- **계산 함수는 LIVE와 BACKTEST가 같은 것**을 쓴다. 증분 계산을 도입할 때도 양쪽에 같은 함수를 쓴다.
- **전광판:** 이벤트 처리 시점의 MT5 입력값(OHLC, HMA, 퍼센타일 밴드, 원비 등), Pure Fact, 처리기 상태를 읽기 전용으로 보여 준다. Consumer는 전광판을 수정할 수 없다.
- **주인 표:** Fact와 처리기의 이름·주인 모듈·사용처를 자동 생성해 문서로 유지하고, 금지된 참조는 정적 검사로 막는다(ATR 분리 규칙의 일반화).

## 5. Consumer(전략) 인터페이스

```python
class Strategy:
    name: str                               # 고유 이름 (알림·기록·상태에 사용)
    def subscriptions(self) -> Subscriptions:   # 관심 심볼·TF·Fact·처리기 상태·이벤트 종류
    def on_event(self, event, board, state, emit) -> None:
        # board: 읽기 전용 전광판
        # state: 이 전략 전용 상태 (엔진이 저장·복원)
        # emit(Signal | TimerRequest): 신호 또는 타이머 요청
```

- 전략은 전광판을 읽고 판단만 한다. 파일·네트워크·시계에 직접 접근하지 않는다.
- 상태는 엔진이 소유한다. 체크포인트 저장·복원은 엔진이 일괄 처리하며, 전략별 상태 파일을 직접 쓰지 않는다.
- 쿨다운, N초 대기, "A 다음 N봉 안에 B"는 `state`와 `TimerRequest`로 표현한다. 이것이 나중에 전략생성기의 부품이 된다.

## 6. Scheduler (타이머)

- 전략은 `TimerRequest(symbol, due_time)`을 낸다. `due_time`은 해당 종목의 `source_time` 기준이다.
- **벽시계는 쓰지 않는다.** LIVE와 BACKTEST 모두 해당 종목의 `MARKET_BUNDLE`이 도착해 그 종목의 `source_time`이 전진할 때만 타이머를 발화한다. 그래서 LIVE와 BACKTEST가 구조적으로 같다.
- 휴장 중에는 그 종목의 틱이 없으므로 타이머가 자연히 멈춘다. 다른 종목(BTC)의 이벤트는 휴장 종목(골드)의 타이머를 발화시키지 않는다.
- **발화 순서:** XAU 묶음이 `source_time = t`로 도착하면 다음 순서로 처리한다.
  1. `due_time < t`인 XAU 타이머를 `(due_time, 요청 순서)` 순으로 먼저 발화한다. 이때 전광판은 아직 이전 묶음 상태이며, 이것이 due_time 시점의 실제 시장 상태다.
  2. 묶음을 전광판에 원자 반영하고 Fact → Stateful Processor → Consumer를 실행한다.
  3. `due_time == t`인 타이머를 발화한다(같은 시각이면 MARKET_BUNDLE 먼저).
- 발화된 `TIMER`는 Ingress Sequencer를 거쳐 `engine_seq`를 받는다.
- 장중에 틱이 뜸하면 타이머는 다음 틱까지 늦게 발화될 수 있다. LIVE는 매 틱 입력이므로 지연은 틱 간격 이내이며, 이는 허용한다.

## 7. 백테스트 데이터와 재생

- **데이터 원천:** 데스크톱 MT5(테스터·과거 데이터)에서 추출한다. 노트북 LIVE 데이터는 옮기지 않는다.
- **형식:** 추출 데이터는 Wire v2 프레임과 같은 형식(S6 MSP3 레코드 재사용)으로 변환해 DuckDB에 적재한다. 파일마다 schema_id, EA 빌드 해시, config 해시를 둔다.
- **재생:** 시장 이벤트를 시각 순서대로 같은 엔진에 쉬지 않고 넣는다. 가상 시계로 기다리지 않는다. TIMER는 현재 전략이 새로 만든다. 필요하면 COMMAND/Watch 등록을 바꿔 넣는다.
- 같은 날을 다시 추출하지 않고 한 번 만든 데이터를 재생한다(D1 워밍업 값이 실행마다 다를 수 있음).
- **LIVE 대조:** 필요할 때 같은 기간을 백테스트로 돌려 텔레그램에 온 알림과 비교한다. 테스터 데이터를 믿어도 되는지는 Part2 재구성 때 며칠치 샘플로 한 번 확인한다.

**재생 해상도 (백테스트 모드)**

| 모드 | 입력 | 용도 | LIVE와 일치 |
|---|---|---|---|
| 봉마감 | 봉 확정 시점만 | 1년치 넓게 훑기 | 봉 확정 기준 전략만 정확 |
| 조건 변화 | 틱을 미리 걸러 봉 확정·밴드/원비 교차 등 조건 관련 값이 바뀐 틱만 | 빠르면서 거의 정확한 검증 | 거름 대상이 전략 조건을 모두 포함하면 정확 |
| 매틱 | 모든 틱 (실제 틱 기반) | 최종 확인, 텔레그램 알림 대조 | 일치 |

- 각 전략은 `subscriptions`에 필요한 해상도(봉 확정만 / 조건 값 변화 / 진행 봉 전체)와 관심 경계(밴드, 원비 등)를 선언한다.
- 재생기는 선택한 모드가 전략의 필요 해상도보다 낮으면 결과에 **"근사치"**를 자동 표시한다.
- 조건 변화 모드의 틱 거르기는 엔진 앞에서 numpy 일괄 처리로 한다(빠름). 거름 대상은 전략 선언에서 자동으로 만든다. 처음 도입할 때는 같은 구간을 매틱 모드와 비교해 결과가 같은지 확인한다. Stateful Processor가 틱 수 등 모든 틱에 의존하는 값을 쓰면 그 전략은 매틱 모드만 정확하다.
- 속도 목표 "1년 ≈ 1시간"은 봉마감 모드 또는 조건 변화 모드 기준이다.

**병렬 실행**
- OZ 후보나 Watch 상태가 자정을 넘을 수 있으므로 **날짜별로 그냥 잘라 병렬 실행하지 않는다.**
- 기본 병렬 단위는 **종목**이다. 종목끼리는 상태를 공유하지 않는다는 전제이며, 종목을 넘나드는 전략이 생기면 그 전략은 한 작업으로 묶는다.
- 기간 병렬이 필요하면 날짜 경계 체크포인트(전일 종료 상태 → 다음 날 시작 상태)를 만든 뒤 그 위에서 나눈다.
- "1년 ≈ 1시간" 목표는 종목 병렬 기준으로 다시 실측한다.

## 8. 출력(김매니저)

- 흐름: `SIGNAL` → 김매니저(문구 생성, 수신자 결정, 중복 방지) → 텔레그램 전송.
- 모든 `SIGNAL`에 `signal_id`를 붙인다(전략 이름, 심볼, `source_time`, 조건 키로 결정적으로 만들어 백테스트에서도 같은 값이 나온다). 김매니저의 중복 방지는 이 `signal_id`로 한다.
- 영구 Outbox는 두지 않는다. 전송 직전에 프로그램이 죽으면 그 알림은 잃을 수 있으며, 이는 허용한다. 텔레그램 채팅 기록이 LIVE 기록이다.
- 전송 실패는 짧게 재시도하고, 그래도 실패하면 로그에 남긴다.
- 백테스트 모드에서는 전송하지 않고 결과 목록만 만든다.
- 명령 해석(command_interpreter + Gemini)은 `COMMAND` → `EXTERNAL_REPLY` → 등록 변경 이벤트 흐름으로 옮긴다.

## 9. 진행 방식 (2덩어리)

**덩어리 1: 엔진과 전체 전략 이전**

1. Ingress Sequencer, 엔진 뼈대, 이벤트 형식, Scheduler, 재생기, Fact 등록부 확장, Stateful Processor 틀, 전광판, 전략 인터페이스를 만든다.
   → **여기서 한 번 멈추고 사용자가 뼈대를 검토한다.**
2. OZ/FVG/SWEEP 상태를 Stateful Processor로 옮기고, INDICATOR, Watch, SPECIAL1~7, OZ/FVG/SWEEP 알림을 Consumer로 이전한다. 판정 로직과 계산식은 그대로 두고, 입력 방식(폴링 → 이벤트)과 상태 보관 위치만 바꾼다.
3. 폴링판(수정본15)과 이벤트판을 같은 입력(합성 240초, 실제 XAU/BTC 캡처, 가능하면 하루치)으로 돌려, 달라진 알림을 **전략별로** 보고한다. 원인은 "판단 시점 변화(정당)"와 "버그"로 분류한다.
4. 같은 입력을 LIVE 경로(파이프)와 재생 경로로 넣었을 때 알림이 완전히 같은지 확인한다.

**덩어리 2: 출력 분리, 섀도 모드, 폴링 종료**

1. 김매니저를 출력 전담으로 분리하고, 명령·Gemini를 이벤트로 옮긴다.
2. **섀도 모드:** 폴링판 LIVE(실제 전송)와 이벤트판 LIVE(텔레그램 전송 차단, 알림 목록만 파일로)를 일정 기간 동시에 돌려 알림을 비교한다. 노트북 부하가 두 배가 되므로 기간은 짧게 잡고, 가능하면 부하가 낮은 시간대나 데스크톱에서 돌린다.
3. 차이를 사용자가 승인하면 이벤트판으로 전환하고 새 기준선을 고정한다.
4. 폴링 경로(SnapshotClient 요청, 전략별 스레드, 가상 시계 실행기)를 제거한다.

## 10. 게이트

- **필수:**

  - 폴링판 대비 차이는 전략별 목록과 원인 분류를 첨부하고, 사용자 승인을 받는다.

  - 모든 이벤트에 `engine_seq`가 있고 연속이다.
  - BUNDLE 원자성 테스트: 전략이 보는 Board의 모든 TF가 같은 묶음 시점이다.
  - `signal_id`가 LIVE 경로와 재생 경로에서 같다.
  - EA 이벤트 발생 주기 측정 결과를 첨부한다(조건 누락 없음 검증의 근거).

## 11. 확정된 결정 (2026-09-26)

1. **같은 시각의 여러 심볼 묶음:** LIVE에서 실제 받은 `engine_seq` 순서 그대로 처리한다. 심볼 이름순으로 다시 정렬하지 않는다.
2. **타이머 기준:** 벽시계가 아니라 해당 종목의 `source_time`이 전진할 때 발화한다. LIVE와 BACKTEST 모두 같고, 발화한 TIMER는 Ingress Sequencer로 넣는다. 휴장 중에는 자연히 멈춘다. `due_time < t`는 묶음 반영 전, `due_time == t`는 묶음 처리 후에 발화한다(6장).
3. **전략 오류:**
   - 예외마다 `STRATEGY_ERROR`를 로그에 남긴다(전략 이름, 시각, 예외 요약).
   - 같은 전략이 연속 5회 실패하면 그 전략의 호출을 멈추고, 시스템 상태를 **DEGRADED**로 표시하고, 텔레그램으로 즉시 알린다. 알림에는 "이 전략의 조건은 현재 보장할 수 없음"을 명시한다.
   - 한 번이라도 성공하면 카운트를 0으로 초기화한다. 자동 복구는 하지 않고, 재시작이나 명령으로만 다시 켠다.
   - 다른 전략은 계속 돈다. 백테스트에서도 같은 규칙으로 동작한다.
   - 전략은 백테스트로 검증된 코드이므로 정상 상황에서는 발동하지 않는 안전장치다.
4. **기록:** 노트북에 영구 이벤트 기록(Journal)을 두지 않는다. LIVE 검증은 텔레그램 알림으로 하고, 백테스트 데이터는 데스크톱 MT5에서 추출한다. 크래시 때 수 초 분량의 입력이나 전송 직전 알림을 잃을 수 있음을 허용한다.
