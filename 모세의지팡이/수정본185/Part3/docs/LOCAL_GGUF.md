# GGUF 실행 — 수정본75

설정 창 → 공통 AI 설정 → AI 실행 방식 **로컬 GGUF**를 선택한다. 설정이 없을 때의 기본 실행 방식도 로컬 GGUF이다. Ollama를 설치하거나 실행할 필요 없이 MOSES가 프로젝트 안의 `llama-server`를 직접 시작한다. 기본 선택 목록은 Ollama·로컬 GGUF·Gemini 세 가지다.

이번 폴더에 준비한 파일:

| 설정 | 입력할 값 |
|---|---|
| 모델을 넣는 전용 폴더 | `models/gguf/` |
| 준비된 GGUF 모델 파일 | `models/gguf/MOSES_Qwen35_4B_Q4_K_M.gguf` |
| GGUF AI 실행기 | `runtime/llama.cpp/llama-server.exe` |

이 수정본의 공통 설정은 GGUF로 준비했다. 기존 Ollama 모델명은 다른 실행 방식의 저장값으로 보존했다. 전용 폴더의 모델을 자동 조회하며, 모델을 드롭다운에서 선택·저장한 다음 대화를 시작하면 된다. 실행기는 프로젝트에 포함된 `runtime/llama.cpp/llama-server.exe`를 자동으로 사용한다. 실행기를 직접 선택할 필요가 없다. 공통 설정은 `settings/ai_settings.json`에 저장한다. 프로젝트 루트부터의 상대 경로이며 `Part3/`를 앞에 붙이지 않는다. 드라이브 문자, 절대 경로, 프로젝트 밖으로 나가는 `..`는 저장할 수 없다.

모델 파일은 사용자가 다운로드 폴더에 준비한 4B GGUF를 복사했다. 현재 설치된 Ollama 모델 본체와 SHA256이 같다. Ollama의 별도 SYSTEM/TEMPLATE/PARAMETER 설정을 변환한 것은 아니며, LoRA 병합·양자화 작업도 이번 범위에 포함하지 않았다.

다른 GGUF를 전용 폴더에 추가하면 설정 창을 열거나 목록 새로고침을 누를 때 자동으로 나타난다. 선택 목록은 파일명 그대로 표시하며 저사양/고사양이나 모델 크기를 따로 분류하지 않는다. 모델 종류와 이름을 나중에 바꾸어도 같은 방식으로 선택한다.

폴더 조회는 모델을 메모리에 올리지 않는다. 사용자가 선택·저장한 모델 하나만 첫 AI 요청에서 자동 로드한다. 선택 전에는 임의로 첫 모델을 사용하는 기본값을 만들지 않는다. 기존 모델을 종료하지 못하면 다음 모델을 로드하지 않는다. 여러 조각으로 나눈 GGUF는 첫 조각만 한 모델로 표시하며 나머지 조각도 같은 폴더에 함께 두어야 한다. 수동 파일 경로는 상세 설정에 남겼다.

## 의존성

현재 MOSES 실행용 Python 환경에서 다음을 실행한다. 통합 설치의 필수 패키지 목록에도 이 가벼운 응답 검증 의존성을 추가했다.

```powershell
python -m pip install -r Part3/requirements-local-gguf.txt
```

GGUF 방식은 PyTorch, Transformers, PEFT, bitsandbytes 또는 llama-cpp-python 설치가 필요하지 않다. 동봉 실행기는 공식 llama.cpp Windows x64 CPU 빌드이며, 실행 파일과 DLL이 있는 `runtime/llama.cpp` 폴더를 함께 유지한다. EXE 패키징이나 새 설치 EXE 제작은 하지 않았다.

## 상세 설정

상세 설정은 처음에는 접혀 있다.

| 항목 | 의미 |
|---|---|
| GGUF AI 실행기 | 기본 실행기는 자동 사용한다. 다른 실행기로 변경할 때만 상대 경로를 지정하며, 비우면 기본값으로 돌아간다. |
| 대화 기억 공간 | 기본 16384 토큰. 전략 계약과 대화가 들어갈 공간이며 크게 하면 메모리를 더 쓴다. |
| GPU로 처리할 모델 층 수 | 기본 0은 CPU. GPU 지원 llama.cpp 실행기를 따로 준비한 경우 양의 정수나 -1을 선택한다. 동봉 CPU 빌드로 GPU 가속은 제공되지 않는다. |
| CPU 작업 스레드 수 | 비우면 실행기가 선택한다. |
| 대화 형식 파일 | 비우면 GGUF에 포함된 형식을 사용한다. 필요할 때 프로젝트 안의 템플릿 파일을 지정한다. |
| 응답 최대 길이 | 비우면 4096 토큰. 너무 작으면 완성되지 않은 JSON을 오류로 반환한다. |
| AI 응답 대기 시간 | 10~300초. 최초 모델 로딩과 해당 추론 요청을 합친 제한이다. |

설정 파일 예시는 다음과 같다. 모델은 사용자가 선택한 파일만 사용한다. 실행기 경로를 생략하거나 비우면 `runtime/llama.cpp/llama-server.exe`를 기본으로 사용한다. 다른 실행기는 상세 설정에서 상대 경로로 지정한다.

```json
{
  "provider": "local_gguf",
  "gguf_model_path": "models/gguf/MOSES_Qwen35_4B_Q4_K_M.gguf",
  "llama_server_path": "runtime/llama.cpp/llama-server.exe",
  "gguf_context_size": 16384,
  "gguf_gpu_layers": 0,
  "timeout": 90
}
```

## 동작과 오류

- 첫 AI 요청에서 모델을 로드하고 실제 준비 상태를 확인한다. 이후 같은 설정은 모델을 재사용한다. 초기화는 대화만 초기화한다.
- 모델 설정을 바꾸거나 다른 실행 방식을 선택하면 기존 소유 모델을 종료한 뒤 다음 요청에서 새 모델을 로드한다. GGUF와 Gemini는 Ollama 연결·실행 모델을 검사하지 않는다. 이전에 MOSES가 Ollama로 요청한 모델이 있으면 그 모델만 종료를 확인하며, 다른 프로그램의 Ollama 모델은 유지한다.
- WATCH, 전략 연구와 백테스트 자연어 명령은 공통 서비스의 같은 모델을 공유한다. 요청을 순서대로 처리하므로 모델이 중복 로드되지 않는다.
- 한 AI 연결을 닫아도 다른 연결이 사용 중이면 모델을 유지한다. 마지막 사용 프로세스가 종료되면 공통 서비스와 모델을 정리한다. 정상 창 닫기는 공통 AI 종료도 확인하며, 공통 서비스 강제 종료 시 Windows Job Object가 소유 GGUF 프로세스를 정리한다.
- 모델 누락, 잘못된 경로·파일, 실행기/DLL/모델 호환 오류, 메모리 부족, 시간 초과, 잘린 JSON은 명확한 오류로 반환한다. 설정을 수정한 뒤 다시 대화할 수 있다.
- JSON 강제 형식과 검증을 유지한다. 기존 Agent, 조회 도구 반복, canonical schema, Recipe v2, validator와 compiler는 그대로 사용한다. 확인 전 전략 적용·파일 생성 동작도 유지한다.

다른 컴퓨터로 옮길 때 프로젝트 전체와 `models/`, `runtime/llama.cpp/`를 함께 복사한다. 파일의 상대 위치를 유지하면 GGUF 경로를 다시 저장할 필요가 없다. Python·MOSES의 기존 실행 환경 설치는 여전히 필요하다.

## 검증

기본 공식 검사는 `python verify_current.py`이며 실제 모델을 로드하지 않는 회귀를 포함한다. 실제 모델 검사는 선택적으로 다음을 실행한다. 현재 실행 중인 Ollama 모델이 있으면 이를 건드리지 않고 검증을 보류한다.

```powershell
python verification/shared_gguf_smoke75.py --model models/gguf/MOSES_Qwen35_4B_Q4_K_M.gguf
```

검증 결과는 `검증결과/GGUF_기본실행기_실모델75.json`에 기록한다. 프로젝트 내 임시 위치로 실행 코드와 상대 경로를 옮겨 실제 추론, 조회 도구 요청·결과 전달, 같은 모델 프로세스 재사용, 한 연결 종료 후 계속 사용 및 전체 종료를 확인한다. 자연어 전략 정확도를 튜닝하거나 실제 MT5 백테스트를 수행하는 검사가 아니다.
