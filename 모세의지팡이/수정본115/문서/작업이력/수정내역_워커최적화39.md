## 2. 단계별 적용

### 1단계 — 입력을 유지한 큰 작업 우선 배정

이미 완성된 청크 목록의 **인덱스 순서만** 바꿉니다. 캡처 메타데이터의 번들 수와 기존 `warm_start~end` 교집합으로 비용을 추정합니다. 메타데이터가 부족하거나 잘못되어 있으면 모든 작업에 같은 단위의 워밍업 포함 기간 길이를 사용합니다. 추정을 위해 캡처 파일을 다시 읽지 않습니다.

단일 워커, 한 번에 모두 실행할 수 있는 작업량, 또는 예상 개선이 5% 미만인 경우 FIFO를 유지합니다. 예상 완료시간이 5% 이상 줄어드는 경우에만 큰 작업을 먼저 배정합니다. **5%는 실제 단축 보장이 아니라 배정 변경 여부를 고르는 추정 임계값**입니다. 동일 비용의 작업은 기존 인덱스 순서로 정렬합니다. 기존 작업 딕셔너리와 내부 설정/캡처를 수정하지 않습니다.

### 2단계 — 제한된 작업 제출과 즉시 보충

이전에는 모든 청크의 Future를 한꺼번에 만들었습니다. 이제 미회수 Future를 **실제 워커당 최대 2개**로 제한하고, 작업 완료를 회수한 직후 진행률 파일 읽기/화면 콜백보다 먼저 다음 작업을 제출합니다. 작업 합치기, 다시 나누기, 이벤트 생략, 엔진 공유, 프로세스 시작 방식 변경은 하지 않습니다.

작업 예외는 그대로 전달합니다. 운영 코드에서 실패한 작업을 자동 재시도하거나 성공으로 처리하지 않습니다. 배정 계산 오류도 기존 FAILED 기록 경로 안에서 처리합니다. 정상 회수 후 CSV를 가져오는 순서는 원래 청크의 시간순으로 고정합니다.

### 3단계 — 부모 진행률 파일 읽기 감소

아직 제출하지 않은 작업의 파일은 읽지 않고, 완료된 작업은 마지막으로 읽은 진행률 JSON을 재사용합니다. 실행 중인 작업은 계속 읽습니다. 파일 잠금·없는 파일·잘못된 JSON은 다음 폴링에 재시도하며, 잘못된 값을 영구 캐시하지 않습니다. 결과 CSV/result.json, 알림 판정, 중단 파일의 워커 내 0.5초 검사 등은 변경하지 않습니다.

`result.json`에 `worker_scheduling` 배정 진단 정보가 추가됩니다. 시간·PID·진행률·배정 정보는 실행에 따라 달라지는 관리 정보이며 알림 CSV 비교 대상과 구분합니다.

## 3. 실제 입력과 검사 방식

제공된 압축의 **XAUUSD+ / BAR / 2026-09-01 / 1,378개 번들**을 사용했습니다. 이 녹화는 수정본36에 들어 있던 입력 파일이며, **수정본36의 운영 코드를 가져온 것은 아닙니다**. 수정본38/39의 실제 워커가 같은 입력을 읽습니다. 입력 파일과 SHA-256은 `replays/captures/real_day`, `input_source.json`에 보관합니다.

두 종류의 부하를 비교했습니다.

1. 기존 하루 전체 단일 청크: 처음부터 끝까지 1,378개 번들을 처리합니다.
2. 배정 검증 전용 6개 고정 출력 구간: 00~03시, 03~05시, 05~07시, 07~09시, 09~13시, 13~24시. 모든 청크가 같은 00시 워밍업 시작을 사용합니다. 합계 **3,298개 번들 = 본구간 1,378개 + 반복 워밍업 1,920개**입니다.

6개 구간은 서로 다른 작업량의 청크를 시험하기 위한 **검증 도구 전용 계획**입니다. 운영 날짜 분할 코드를 바꾸지 않았으며 실제 1주 녹화를 만들거나 복원한 것이 아닙니다. 검증 설정의 `overlap_trading_days=0`은 양쪽에 동일하게 적용했고 운영 기본 3거래일은 유지했습니다.

검증 환경: Linux / Python 3.13.5 / NumPy 2.3.5 / spawn 프로세스풀 / 병렬 2워커 / 측정 CPU affinity 0,1. affinity는 검증 도구에만 설정했습니다. 운영 코드의 CPU 고정·BLAS 스레드 수·워커 수를 변경하지 않았습니다.
